8. Testing, Git, DevOps và bảo mật

8.1. Testing Bắt buộc

JD mức Middle thường ghi "viết unit test" và hỏi bạn test cái gì, mock thế nào. Kim tự tháp test: nhiều unit test (nhanh, rẻ), vừa phải integration test (API + DB thật), ít E2E test (chậm, dễ chập chờn).

LoạiCông cụTest cái gì
UnitVitest, Jest, node:testHàm thuần, service (mock repository)
Integration / APISupertest + DB test (Testcontainers hoặc Docker)Route → service → DB thật, status code, response

  • Cấu trúc AAA: Arrange (chuẩn bị), Act (thực hiện), Assert (kiểm tra). Mỗi test kiểm tra một hành vi và có tên mô tả hành vi đó.
  • Test hành vi, không test chi tiết cài đặt. Với RTL, tìm phần tử theo role/label (getByRole), không theo class CSS.
  • Mock những thứ nằm ngoài tầm kiểm soát: API bên thứ ba, thời gian (vi.useFakeTimers), email. Đừng mock mọi thứ, nếu không test sẽ không còn ý nghĩa.
  • Độ phủ (coverage) 70–80% là mục tiêu hợp lý. Coverage cao chưa chắc test đã tốt.

8.2. Git và quy trình làm việc nhóm Bắt buộc

  • Lệnh hằng ngày: branch, switch, commit, pull --rebase, push, stash, log --oneline --graph. Lệnh cứu hộ: reflog, revert, reset, cherry-pick.
  • Merge và rebase: merge giữ nguyên lịch sử và tạo merge commit. Rebase viết lại lịch sử cho thẳng hàng. Không rebase nhánh đã push mà người khác đang dùng.
  • Mô hình nhánh: GitHub Flow hoặc trunk-based (nhánh tính năng ngắn ngày → PR → main), hoặc Git Flow (develop, release, hotfix) ở công ty có lịch release cố định.
  • Conventional Commits: feat:, fix:, refactor:, chore:... PR nhỏ, có mô tả và có test. Khi review thì góp ý cụ thể và lịch sự.
  • Công cụ chất lượng code: ESLint, Prettier, Husky + lint-staged (chạy lint trước khi commit), TypeScript strict.

8.3. Docker Bắt buộc

  • Image là bản đóng gói chỉ đọc; container là một image đang chạy. Mỗi lệnh trong Dockerfile tạo một layer được cache, nên hãy copy package*.json và cài dependency trước khi copy source.
  • Multi-stage build cho image nhỏ: stage build có devDependencies, stage chạy chỉ giữ thứ cần thiết.
  • Thêm .dockerignore (bỏ node_modules, .env, .git), chạy bằng user không phải root, và không đóng gói secret vào image.
```dockerfile # ---- build ---- FROM node:24-alpine AS build WORKDIR /app COPY package*.json ./ RUN npm ci COPY . . RUN npm run build && npm prune --omit=dev # ---- runtime ---- FROM node:24-alpine ENV NODE_ENV=production WORKDIR /app COPY --from=build /app/node_modules ./node_modules COPY --from=build /app/dist ./dist COPY package.json ./ USER node EXPOSE 3000 CMD ["node", "dist/main.js"] ``` ```yaml # docker-compose.yml cho môi trường dev: app + Postgres + Redis services: api: build: . ports: ["3000:3000"] env_file: .env depends_on: db: { condition: service_healthy } redis: { condition: service_started } db: image: postgres:17 environment: { POSTGRES_PASSWORD: secret, POSTGRES_DB: app } volumes: [pgdata:/var/lib/postgresql/data] healthcheck: { test: ["CMD-SHELL", "pg_isready -U postgres"], interval: 5s, retries: 10 } redis: image: redis:7-alpine volumes: pgdata: ```

8.4. CI/CD và triển khai Nên biết

  • CI (mỗi PR): cài dependency → lint → type-check → test → build. CD (khi merge vào main): build image → đẩy lên registry → deploy (VPS, ECS, Kubernetes, Vercel cho Next.js).
  • Nginx làm reverse proxy: kết thúc TLS, nén, phục vụ file tĩnh, chuyển request về app Node. Chạy app bằng PM2 nếu deploy thẳng trên VPS.
  • Quản lý secret: biến môi trường của nền tảng, GitHub Secrets, AWS Secrets Manager, Vault. Không bao giờ commit file .env.
  • Quan sát hệ thống (observability): log (Loki, ELK), metrics (Prometheus + Grafana), tracing (OpenTelemetry), bắt lỗi (Sentry).
  • Điểm cộng Kiến thức cơ bản về Kubernetes (Pod, Deployment, Service, Ingress) và AWS (EC2, S3, RDS, CloudFront).
```yaml # .github/workflows/ci.yml name: CI on: [pull_request] jobs: test: runs-on: ubuntu-latest services: postgres: image: postgres:17 env: { POSTGRES_PASSWORD: test } ports: ["5432:5432"] steps: - uses: actions/checkout@v4 - uses: actions/setup-node@v4 with: { node-version: 24, cache: npm } - run: npm ci - run: npm run lint && npm run typecheck - run: npm test env: { DATABASE_URL: "postgresql://postgres:test@localhost:5432/postgres" } ```

Bạn viết loại nào nhiều nhất? A: Unit test kiểm tra một hàm hoặc một class, phần phụ thuộc thì mock, chạy rất nhanh. Integration test kiểm tra nhiều thành phần chạy cùng nhau, ví dụ API với DB thật. E2E chạy trên trình duyệt thật theo luồng của người dùng. Theo kim tự tháp test thì unit test nhiều nhất; tuy vậy với API backend, integration test qua Supertest thường đem lại nhiều giá trị nhất. Q: Khi nào nên mock, khi nào không? A: Nên mock những thứ chậm, không ổn định hoặc gây tác dụng phụ: API bên ngoài, email, thanh toán, thời gian, số ngẫu nhiên. Không nên mock chính thứ đang test, và với integration test thì hạn chế mock DB (dùng DB test trong Docker). Mock quá nhiều khiến test vẫn pass trong khi code thật đã hỏng. Q: Merge và rebase khác nhau thế nào? Khi nào không được rebase? A: Merge tạo một merge commit và giữ nguyên lịch sử gốc. Rebase đặt lại các commit của bạn lên trên nhánh đích để lịch sử thẳng hàng, nhưng điều đó làm đổi hash của commit. Không rebase những nhánh đã push mà người khác đang làm việc trên đó. Q: Vì sao trong Dockerfile phải COPY package.json trước rồi mới COPY source? A: Để tận dụng cache của layer. Khi chỉ sửa code mà không đổi dependency, layer `npm ci` được dùng lại nên build nhanh hơn rất nhiều. Q: Multi-stage build có lợi gì? A: Image cuối cùng chỉ chứa code đã build và dependency để chạy, không có devDependencies, source TS hay công cụ build. Nhờ vậy image nhỏ hơn, deploy nhanh hơn và ít bề mặt tấn công hơn. Q: Trình bày XSS và cách React chống XSS. A: XSS là khi kẻ tấn công chèn được script vào trang, script đó chạy trên trình duyệt nạn nhân và lấy cắp token hay thực hiện hành động thay họ. React tự escape mọi giá trị được render qua `{}`. Rủi ro còn lại nằm ở `dangerouslySetInnerHTML`, ở URL dạng `javascript:` trong href, và ở thư viện bên thứ ba. Biện pháp bổ sung: sanitize bằng DOMPurify, đặt header CSP, để token trong cookie HttpOnly. Q: CSRF là gì, và nếu dùng JWT trong header Authorization thì có bị CSRF không? A: CSRF là khi trang web khác khiến trình duyệt của nạn nhân gửi request kèm cookie của họ tới site của bạn. Nếu token được gửi qua header Authorization (do JS gắn vào) thì trình duyệt không tự gửi, nên không bị CSRF. Ngược lại, khả năng bị XSS lấy token lại cao hơn. Nếu xác thực bằng cookie thì cần SameSite và/hoặc CSRF token. Q: Lỗi IDOR là gì? A: Insecure Direct Object Reference: API chỉ kiểm tra là user đã đăng nhập, mà không kiểm tra tài nguyên có thuộc về user đó không. Kẻ tấn công chỉ cần đổi id trong URL. Phòng chống: luôn lọc theo chủ sở hữu hoặc kiểm tra policy ở tầng service. Q: Bạn quản lý secret (mật khẩu DB, API key) thế nào? A: Để trong biến môi trường hoặc trình quản lý secret của nền tảng (GitHub Secrets, AWS Secrets Manager, Vault). Có file `.env.example` không chứa giá trị thật; `.env` nằm trong `.gitignore`. Không đóng gói secret vào image, không ghi secret ra log.
