3. Backend framework và thiết kế API

Ở mức Middle, bạn cần dựng được một API chạy production: có cấu trúc rõ ràng, validate input, xác thực, xử lý lỗi tập trung và ghi log. Biết Express (phổ biến nhất) và NestJS (doanh nghiệp ưa dùng, cách tổ chức rất giống Laravel).

3.1. Express Bắt buộc

  • Middleware là hàm (req, res, next), chạy theo đúng thứ tự khai báo. Middleware hoặc gửi response, hoặc gọi next() để chuyển tiếp.
  • Error middleware có 4 tham số (err, req, res, next) và đặt ở cuối cùng. Từ Express 5, lỗi trong hàm async tự động được chuyển tới middleware này mà không cần try/catch.
  • express.Router() chia route theo module. Đặt helmet, cors, express.json({ limit }) và rate limit ở đầu.
```ts import express from 'express'; import helmet from 'helmet'; import cors from 'cors'; import { pinoHttp } from 'pino-http'; const app = express(); app.use(helmet()); app.use(cors({ origin: ['https://app.example.com'], credentials: true })); app.use(express.json({ limit: '1mb' })); app.use(pinoHttp()); app.use('/api/v1/users', usersRouter); // 404 app.use((req, res) => res.status(404).json({ code: 'NOT_FOUND', message: 'Route không tồn tại' })); // Error handler tập trung: luôn đặt cuối cùng app.use((err, req, res, next) => { const status = err.statusCode ?? 500; if (status >= 500) req.log.error(err); res.status(status).json({ code: err.code ?? 'INTERNAL_ERROR', message: status >= 500 ? 'Lỗi hệ thống' : err.message, // không lộ stack trace ra ngoài }); }); ```

Các loại middleware và cách tự viết

  • Application-level (app.use), router-level (router.use), route-level (truyền vào từng route: router.post('/', auth, validate(schema), handler)).
  • Built-in: express.json(), express.urlencoded(), express.static(). Bên thứ ba: helmet, cors, cookie-parser, compression, express-rate-limit, multer.
  • Gọi next() để chuyển sang middleware tiếp theo; next(err) để nhảy thẳng tới error handler. Một middleware phải hoặc gửi response, hoặc gọi next; nếu không làm gì thì request bị treo.
```ts import { randomUUID } from 'node:crypto'; // Gắn requestId và đo thời gian xử lý cho mọi request export function requestContext(req, res, next) { req.id = req.get('x-request-id') ?? randomUUID(); res.setHeader('x-request-id', req.id); const start = process.hrtime.bigint(); res.on('finish', () => { const ms = Number(process.hrtime.bigint() - start) / 1e6; req.log?.info({ status: res.statusCode, ms }, `${req.method} ${req.originalUrl}`); }); next(); } ```

Xử lý lỗi async: Express 4 và Express 5

Ở Express 4, lỗi trong hàm async không được chuyển tới error handler: request bị treo và xuất hiện cảnh báo unhandled rejection. Phải bọc lại bằng một wrapper hoặc dùng gói express-async-errors. Ở Express 5, promise bị reject sẽ tự động được chuyển thành next(err).

```ts // Express 4: wrapper bắt buộc phải có const asyncHandler = (fn) => (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next); router.get('/:id', asyncHandler(async (req, res) => { res.json(await productService.findById(Number(req.params.id))); })); // Express 5: viết thẳng, lỗi tự tới error handler router.get('/:id', async (req, res) => { res.json(await productService.findById(Number(req.params.id))); }); ```

Những thay đổi khác của Express 5 cần biết khi nâng cấp: cú pháp đường dẫn mới (wildcard phải có tên, ví dụ /files/*path; tham số tùy chọn viết là /:file{.:ext}), req.query chỉ đọc được chứ không gán lại được, bỏ các hàm cũ như app.del và res.sendfile, yêu cầu Node 18 trở lên.

Cấu trúc một module Express theo lớp

```ts // src/modules/products/products.routes.ts const router = Router(); router.get('/', validate(ListQuery, 'query'), productsController.list); router.get('/:id', productsController.get); router.post('/', requireAuth, requireRole('admin'), validate(CreateProduct), productsController.create); export default router; // products.controller.ts: chỉ lo HTTP export const productsController = { async list(req, res) { res.json(await productsService.list(req.query)); }, async get(req, res) { res.json(await productsService.get(Number(req.params.id))); }, async create(req, res) { res.status(201).json(await productsService.create(req.body, req.user.id)); }, }; // products.service.ts: nghiệp vụ, không biết req/res nên dễ unit test export const productsService = { async get(id: number) { const p = await productsRepo.findById(id); if (!p) throw new NotFoundError('Sản phẩm'); return p; }, // ... }; // app.ts: tách tạo app khỏi listen để Supertest dùng được app mà không mở port export function createApp() { const app = express(); app.use(helmet(), express.json({ limit: '1mb' }), requestContext); app.use('/api/v1/products', productsRouter); app.use(notFoundHandler); app.use(errorHandler); return app; } // server.ts createApp().listen(env.PORT); ```

Điểm cộng Fastify là lựa chọn thay thế Express: nhanh hơn đáng kể, validate và serialize theo JSON Schema, có hệ thống plugin và hook rõ ràng, hỗ trợ TypeScript tốt. NestJS chạy được trên cả Express lẫn Fastify.

Module: imports, exports, global, dynamic module

  • Mỗi module khai báo controllers, providers, imports (dùng provider mà module khác đã export) và exports (cho module khác dùng provider của mình). Provider không được export thì module khác không inject được; đây là lỗi "Nest can't resolve dependencies" hay gặp nhất.
  • @Global() cho module dùng ở khắp nơi (config, logger). Đừng lạm dụng.
  • Dynamic module là module nhận cấu hình lúc import: ConfigModule.forRoot(), TypeOrmModule.forRootAsync({ useFactory }), JwtModule.registerAsync().
  • Hai module phụ thuộc vòng lẫn nhau thì cần forwardRef(() => OtherModule). Đây thường là dấu hiệu nên tách thêm một module chung.

3.3. Thiết kế REST API Bắt buộc

  • URL là danh từ số nhiều, còn hành động thể hiện bằng HTTP method: GET /orders, POST /orders, GET /orders/42, PATCH /orders/42, DELETE /orders/42. Tài nguyên con viết dạng GET /users/7/orders.
  • Idempotent: gọi nhiều lần cho cùng kết quả. GET, PUT, DELETE là idempotent; POST thì không. Với API thanh toán, hãy nhận header Idempotency-Key để tránh trừ tiền hai lần khi client gửi lại request.
  • PUT thay thế toàn bộ tài nguyên; PATCH chỉ cập nhật một phần.
  • Versioning: /api/v1/... là cách phổ biến nhất.
  • Response nhất quán: cùng một dạng cho lỗi (code, message, details) và cho danh sách (data, meta). Tài liệu hóa bằng OpenAPI/Swagger.

3.4. Validate input Bắt buộc

Không bao giờ tin dữ liệu từ client. Validate body, params và query ở ngay đầu vào: dùng zod với Express, class-validator với NestJS. Với zod, một schema cho bạn cả bước validate lẫn kiểu TypeScript.

```ts import { z } from 'zod'; const CreateUser = z.object({ email: z.string().email(), password: z.string().min(8), age: z.coerce.number().int().min(16).optional(), }); type CreateUser = z.infer; // kiểu TS sinh ra từ schema const validate = (schema) => (req, res, next) => { const r = schema.safeParse(req.body); if (!r.success) return res.status(400).json({ code: 'VALIDATION_ERROR', details: r.error.issues }); req.body = r.data; // dữ liệu đã được làm sạch, các trường lạ bị loại bỏ next(); }; router.post('/', validate(CreateUser), createUserHandler); ```

Mô hình hay dùng: access token (JWT, sống 5–15 phút) gửi qua header Authorization: Bearer; refresh token (7–30 ngày) lưu trong cookie HttpOnly, Secure, SameSite và trong DB. Mỗi lần refresh thì cấp refresh token mới và vô hiệu hóa token cũ (rotation). Nếu thấy một refresh token cũ bị dùng lại, hãy thu hồi cả chuỗi token vì có thể nó đã bị đánh cắp.

  • Hash mật khẩu bằng bcrypt (cost 10–12) hoặc argon2id. Tuyệt đối không dùng MD5/SHA1.
  • JWT chỉ được ký, không được mã hóa: ai cũng đọc được payload, nên đừng để thông tin nhạy cảm trong đó.
  • RBAC: user → role → permission. Ngoài việc kiểm tra role, phải kiểm tra quyền sở hữu tài nguyên (đơn hàng 42 có đúng là của user này không), nếu không sẽ dính lỗi IDOR.
  • Nên biết OAuth2 / OpenID Connect: luồng Authorization Code + PKCE để đăng nhập bằng Google/GitHub (thư viện Passport.js, Auth.js).
```ts import jwt from 'jsonwebtoken'; export const requireAuth = (req, res, next) => { const token = req.headers.authorization?.replace('Bearer ', ''); if (!token) return res.status(401).json({ code: 'UNAUTHORIZED' }); try { req.user = jwt.verify(token, env.JWT_SECRET, { algorithms: ['HS256'] }); next(); } catch { res.status(401).json({ code: 'TOKEN_INVALID' }); } }; export const requireRole = (...roles) => (req, res, next) => roles.includes(req.user.role) ? next() : res.status(403).json({ code: 'FORBIDDEN' }); ```

3.6. Kiến trúc và vận hành Nên biết

  • Chia lớp: Controller (nhận HTTP, validate) → Service (nghiệp vụ, không biết gì về req/res) → Repository (truy cập DB). Chia như vậy thì dễ test và dễ đổi DB.
  • Cấu trúc thư mục theo tính năng (modules/orders, modules/users) thay vì theo loại file (controllers/, services/) khi dự án lớn dần.
  • Logging: log có cấu trúc (JSON) bằng pino, gắn requestId vào từng dòng để lần theo một request. Không ghi log mật khẩu hay token.
  • Graceful shutdown: khi nhận SIGTERM thì ngừng nhận request mới, xử lý nốt request đang chạy, đóng kết nối DB, rồi thoát.
  • Health check: /health (app còn sống) và /ready (DB, Redis sẵn sàng) cho load balancer và Kubernetes.
  • Upload file: file nhỏ thì dùng multer; file lớn thì cấp presigned URL để client upload thẳng lên S3, server không phải chuyển tiếp dữ liệu.
```ts const server = app.listen(env.PORT); process.on('SIGTERM', () => { server.close(async () => { // ngừng nhận kết nối mới, chờ request đang chạy xong await prisma.$disconnect(); await redis.quit(); process.exit(0); }); setTimeout(() => process.exit(1), 10_000).unref(); // quá 10 giây thì buộc thoát }); ```

Vì sao thứ tự khai báo lại quan trọng? A: Express chạy middleware theo đúng thứ tự `app.use` hoặc thứ tự route. Mỗi middleware có thể sửa `req`/`res`, gửi response, hoặc gọi `next()` để chuyển tiếp. Ví dụ: nếu đặt `express.json()` sau router thì `req.body` sẽ là undefined; nếu error handler không nằm cuối thì nó không bắt được lỗi của các route khai báo sau. Q: Trình bày luồng xử lý một request trong NestJS. A: Middleware → Guard (có được phép vào không?) → Interceptor (phần trước handler) → Pipe (validate/transform tham số) → Controller → Service → Interceptor (phần sau handler, ví dụ bọc response) → nếu có lỗi thì Exception Filter định dạng response lỗi. Q: PUT và PATCH khác nhau thế nào? Phương thức nào idempotent? A: PUT gửi toàn bộ tài nguyên để thay thế, PATCH chỉ gửi các trường cần sửa. GET, PUT, DELETE (và HEAD, OPTIONS) là idempotent. POST không idempotent. PATCH tùy cách cài đặt: `{ "stock": 5 }` thì idempotent, còn "tăng thêm 1" thì không. Q: 401 và 403 khác nhau ra sao? A: 401 là chưa xác thực: không có token, token sai hoặc đã hết hạn, client cần đăng nhập lại. 403 là đã biết bạn là ai nhưng bạn không có quyền với tài nguyên này. Q: Lưu JWT ở localStorage hay cookie? Vì sao? A: localStorage bị JS đọc được, nên dính XSS là mất token. Cookie HttpOnly thì JS không đọc được, nhưng phải chống CSRF bằng SameSite=Lax/Strict hoặc CSRF token. Cách hay dùng: access token ngắn hạn giữ trong bộ nhớ (biến JS), refresh token để trong cookie HttpOnly, Secure, SameSite. Q: Làm sao thu hồi JWT trước khi nó hết hạn? A: Để access token sống ngắn (5–15 phút) rồi thu hồi refresh token trong DB. Nếu cần chặn ngay thì giữ blacklist `jti` trong Redis cho đến khi token hết hạn, hoặc lưu `tokenVersion` của user và tăng giá trị đó khi đăng xuất khỏi mọi thiết bị. Q: Vì sao cursor pagination nhanh hơn offset với bảng lớn? A: `OFFSET 100000` buộc DB đọc rồi bỏ đi 100.000 dòng. Cursor dùng `WHERE (created_at, id) < (...)`, đi thẳng vào index nên tốc độ không phụ thuộc trang thứ mấy. Thêm nữa, khi có dòng mới được chèn vào thì cursor không bị trùng hay sót dữ liệu. Q: Khi nào nên dùng hàng đợi thay vì xử lý ngay trong request? A: Khi việc đó chậm (gửi email, xuất file, xử lý ảnh), có thể lỗi và cần thử lại (gọi API bên thứ ba), cần lên lịch, hoặc cần giới hạn tốc độ. Request chỉ đẩy job vào hàng đợi rồi trả 202 hoặc 201 ngay, worker sẽ xử lý sau. Q: Graceful shutdown là gì và vì sao cần? A: Khi deploy, Kubernetes hoặc Docker gửi tín hiệu SIGTERM. App cần ngừng nhận request mới, chạy nốt request đang dở, đóng kết nối DB/Redis rồi mới thoát. Không làm vậy thì người dùng bị lỗi 502 giữa chừng và có thể hỏng dữ liệu. Q: Express 4 và Express 5 xử lý lỗi trong hàm async khác nhau thế nào? A: Express 4 không bắt promise bị reject: request bị treo và xuất hiện unhandled rejection, nên phải bọc handler bằng asyncHandler (`.catch(next)`) hoặc dùng `express-async-errors`. Q: `res.locals` dùng để làm gì? A: Là nơi lưu dữ liệu trong phạm vi một request, dùng chung giữa các middleware, ví dụ user đã xác thực, requestId hay kết quả đã tính trước. Dữ liệu này hết hiệu lực khi request kết thúc. Q: Lỗi "Nest can't resolve dependencies of X" nghĩa là gì và sửa thế nào? A: Nest không tìm thấy provider mà X cần inject. A: Mặc định là singleton, một instance dùng chung cho toàn app. Vì vậy không được lưu dữ liệu riêng của request (user hiện tại, giỏ hàng) trong thuộc tính của service, nếu không các request sẽ ghi đè lẫn nhau. 4. GraphQL

GraphQL là một ngôn ngữ truy vấn cho API: client mô tả chính xác dữ liệu cần lấy, server trả về đúng như vậy qua một endpoint duy nhất (POST /graphql). Nó hay gặp ở các sản phẩm có nhiều client (web, mobile) và dữ liệu lồng nhau phức tạp.

4.1. Khái niệm cốt lõi Bắt buộc

  • Schema (SDL): khai báo kiểu dữ liệu và các thao tác. Đây là "hợp đồng" giữa frontend và backend.
  • Query để đọc, Mutation để ghi, Subscription để nhận dữ liệu realtime (thường qua WebSocket).
  • Resolver: hàm trả dữ liệu cho từng field. Resolver nhận (parent, args, context, info); context chứa user đã đăng nhập, DataLoader, kết nối DB.
  • Kiểu: scalar (Int, String, ID...), ! là bắt buộc, [Post!]! là danh sách, input dùng cho tham số, ngoài ra có enum, interface, union.
```graphql type User { id: ID! name: String! posts(first: Int = 10): [Post!]! } type Post { id: ID! title: String! author: User! } input CreatePostInput { title: String!, body: String! } type Query { me: User post(id: ID!): Post } type Mutation { createPost(input: CreatePostInput!): Post! } ``` ```graphql # Client chỉ lấy đúng những field cần: không thừa, không thiếu query Dashboard { me { name posts(first: 5) { id title } } } ```

4.2. Bài toán N+1 và DataLoader Bắt buộc

Đây là câu hỏi GraphQL hay gặp nhất. Query 20 bài viết kèm author thì resolver Post.author chạy 20 lần, tức 1 query lấy bài viết + 20 query lấy user. DataLoader gom các id trong cùng một tick thành một query WHERE id IN (...) và cache kết quả trong phạm vi request đó.

```ts import DataLoader from 'dataloader'; // Tạo DataLoader MỚI cho mỗi request (trong context), để không lẫn cache giữa các user const createLoaders = () => ({ userById: new DataLoader(async (ids: readonly string[]) => { const users = await prisma.user.findMany({ where: { id: { in: [...ids] } } }); const map = new Map(users.map((u) => [u.id, u])); return ids.map((id) => map.get(id) ?? null); // PHẢI trả về đúng thứ tự của ids }), }); const resolvers = { Query: { post: (_, { id }) => prisma.post.findUnique({ where: { id } }), }, Post: { author: (post, _, ctx) => ctx.loaders.userById.load(post.authorId), }, Mutation: { createPost: (_, { input }, ctx) => { if (!ctx.user) throw new GraphQLError('Chưa đăng nhập', { extensions: { code: 'UNAUTHENTICATED' } }); return prisma.post.create({ data: { ...input, authorId: ctx.user.id } }); }, }, }; ```

4.4. Bảo mật, phân trang, công cụ Nên biết

  • Chống query độc hại: giới hạn độ sâu (depth limit), giới hạn độ phức tạp (cost/complexity), giới hạn số phần tử mỗi trang, đặt timeout. Với app nội bộ thì chỉ cho chạy các query đã đăng ký trước (persisted queries).
  • Phân quyền đặt ở tầng resolver/service, kể cả với field lồng nhau (ví dụ User.email chỉ chủ tài khoản mới xem được).
  • Phân trang: chuẩn Relay Connection gồm edges { node cursor } và pageInfo { hasNextPage endCursor }, tức cursor-based.
  • Server: Apollo Server, GraphQL Yoga, hoặc @nestjs/graphql với hai cách: code-first (sinh schema từ decorator TS) hoặc schema-first.
  • Client: Apollo Client (có cache chuẩn hóa theo __typename + id), urql, hoặc TanStack Query kết hợp graphql-request.
  • Điểm cộng Federation: gộp schema của nhiều microservice thành một graph chung qua gateway (Apollo Router). Xem thêm phần Microservices.
```qa Q: GraphQL giải quyết vấn đề gì của REST? 5. Database: SQL, NoSQL, Redis

Đây là thế mạnh mang theo từ PHP của bạn. Ở mức Middle, bạn cần thiết kế được schema, đọc được EXPLAIN, dùng transaction đúng chỗ và biết khi nào cần cache.

5.1. SQL và thiết kế schema Bắt buộc

  • JOIN: INNER (chỉ dòng khớp ở cả hai bảng), LEFT (giữ mọi dòng bảng trái), RIGHT, FULL. GROUP BY + HAVING, subquery, CTE (WITH), window function (ROW_NUMBER() OVER (PARTITION BY ...)).
  • Chuẩn hóa (1NF–3NF) để tránh trùng dữ liệu; phi chuẩn hóa có chủ đích (lưu thêm total_amount, comment_count) để đọc nhanh hơn.
  • Khóa ngoại, ràng buộc UNIQUE, NOT NULL, CHECK. Giá tiền dùng kiểu DECIMAL/số nguyên (đơn vị nhỏ nhất), không dùng FLOAT.
  • Xóa mềm (deleted_at), cột created_at/updated_at, nên dùng UUID hay số tự tăng.
  • PostgreSQL hiện được nhiều nơi ưa chuộng: có JSONB, kiểu mảng, RETURNING, partial index.
```sql -- Top 3 sản phẩm bán chạy nhất trong từng danh mục, tháng này WITH sales AS ( SELECT p.category_id, p.id, p.name, SUM(oi.quantity) AS sold FROM order_items oi JOIN orders o ON o.id = oi.order_id AND o.status = 'paid' JOIN products p ON p.id = oi.product_id WHERE o.created_at >= date_trunc('month', now()) GROUP BY p.category_id, p.id, p.name ) SELECT * FROM ( SELECT *, ROW_NUMBER() OVER (PARTITION BY category_id ORDER BY sold DESC) AS rn FROM sales ) t WHERE rn <= 3; ```

5.2. Index và tối ưu query Bắt buộc

  • Index mặc định là B-tree, dùng tốt cho =, <, >, BETWEEN, ORDER BY và LIKE 'abc%'. Nó không giúp được LIKE '%abc', hay khi bọc cột trong hàm (WHERE LOWER(email) = ..., trừ khi tạo index theo biểu thức).
  • Composite index (a, b, c) theo quy tắc leftmost prefix: dùng được cho điều kiện trên a, a,b, a,b,c, nhưng không dùng được khi chỉ lọc theo b. Nên đặt cột lọc bằng = trước, cột lọc theo khoảng hoặc sắp xếp sau.
  • Covering index: index chứa đủ mọi cột mà query cần, nên DB không phải đọc bảng.
  • Index giúp đọc nhanh nhưng làm chậm việc ghi và tốn dung lượng. Đừng đánh index mọi cột.
  • Đọc EXPLAIN ANALYZE: Seq Scan trên bảng lớn là dấu hiệu xấu; số dòng ước lượng lệch nhiều so với thực tế thì cần chạy ANALYZE để cập nhật thống kê.
  • Lỗi N+1 với ORM: lặp qua danh sách đơn hàng rồi query user cho từng đơn. Sửa bằng include/JOIN (giống with() trong Eloquent).
  • Dùng connection pool, đặt giới hạn số kết nối hợp lý (max), và không mở kết nối mới cho mỗi request.
```sql -- Query: đơn hàng của user, mới nhất trước SELECT id, total, created_at FROM orders WHERE user_id = 42 AND status = 'paid' ORDER BY created_at DESC LIMIT 20; -- Index phù hợp: cột lọc bằng "=" trước, cột sắp xếp sau CREATE INDEX idx_orders_user_status_created ON orders (user_id, status, created_at DESC); EXPLAIN ANALYZE SELECT ...; -- mong đợi thấy: Index Scan using idx_orders_user_status_created ```

Bài toán kinh điển: hai người cùng mua món hàng cuối cùng trong kho. Ba cách giải:

```sql -- Cách 1 (đơn giản, tốt nhất cho trường hợp này): UPDATE có điều kiện, nguyên tử UPDATE products SET stock = stock - 1 WHERE id = 7 AND stock >= 1; -- affected rows = 0 → hết hàng -- Cách 2: pessimistic lock, khóa dòng cho đến khi commit BEGIN; SELECT stock FROM products WHERE id = 7 FOR UPDATE; -- kiểm tra stock trong code, rồi UPDATE COMMIT; -- Cách 3: optimistic lock bằng cột version UPDATE products SET stock = 4, version = version + 1 WHERE id = 7 AND version = 12; -- affected rows = 0 → có người khác đã sửa trước, đọc lại rồi thử lại ``` ```ts // Prisma: chuyển tiền phải nằm trong một transaction await prisma.$transaction(async (tx) => { const from = await tx.account.update({ where: { id: fromId }, data: { balance: { decrement: amount } } }); if (from.balance < 0) throw new Error('Không đủ số dư'); // throw → rollback toàn bộ await tx.account.update({ where: { id: toId }, data: { balance: { increment: amount } } }); }); ```

5.5. MongoDB Nên biết

  • Lưu dạng document (BSON), schema linh hoạt. Thiết kế theo cách dữ liệu được đọc, không theo chuẩn hóa.
  • Embed (nhúng) khi dữ liệu con luôn được đọc cùng cha và số lượng có giới hạn, ví dụ địa chỉ trong user. Reference khi dữ liệu con nhiều vô hạn hoặc được dùng ở nhiều nơi, ví dụ comment hay đơn hàng. Một document tối đa 16 MB.
  • Index (single, compound, text, TTL), aggregation pipeline ($match → $group → $sort → $lookup). ODM phổ biến là Mongoose.
  • Có transaction nhiều document (cần replica set), nhưng nếu dùng quá nhiều thì nên cân nhắc chuyển sang SQL.
```js // Doanh thu theo ngày của 7 ngày gần nhất db.orders.aggregate([ { $match: { status: 'paid', createdAt: { $gte: new Date(Date.now() - 7 * 864e5) } } }, { $group: { _id: { $dateToString: { format: '%Y-%m-%d', date: '$createdAt' } }, revenue: { $sum: '$total' } } }, { $sort: { _id: 1 } }, ]); ```

5.6. Redis và cache Bắt buộc

  • Kiểu dữ liệu: String, Hash, List, Set, Sorted Set (bảng xếp hạng), Stream. Mọi lệnh đều là nguyên tử vì Redis thực thi lệnh trên một luồng.
  • Dùng cho: cache, session, rate limit, hàng đợi (BullMQ), pub/sub, khóa phân tán, đếm lượt xem.
  • Cache-aside (phổ biến nhất): đọc cache, không có thì đọc DB rồi ghi vào cache kèm TTL. Khi ghi dữ liệu thì xóa key cache thay vì cập nhật nó.
  • Các vấn đề cần biết: cache stampede (key hot hết hạn, nghìn request cùng đập vào DB; xử lý bằng lock hoặc làm mới sớm), cache penetration (query key không tồn tại liên tục; cache cả giá trị null), nhiều key hết hạn cùng lúc (thêm độ lệch ngẫu nhiên cho TTL).
```ts async function getProduct(id: number) { const key = `product:${id}`; const cached = await redis.get(key); if (cached) return JSON.parse(cached); const product = await prisma.product.findUnique({ where: { id } }); const ttl = 300 + Math.floor(Math.random() * 60); // 5–6 phút, lệch ngẫu nhiên await redis.set(key, JSON.stringify(product ?? null), 'EX', product ? ttl : 30); return product; } async function updateProduct(id: number, data) { const p = await prisma.product.update({ where: { id }, data }); await redis.del(`product:${id}`); // xóa cache sau khi ghi DB return p; } // Rate limit fixed window: tối đa 100 request/phút cho mỗi IP async function rateLimit(ip: string) { const key = `rl:${ip}:${Math.floor(Date.now() / 60000)}`; const n = await redis.incr(key); if (n === 1) await redis.expire(key, 60); return n <= 100; } ``` ```qa Q: INNER JOIN và LEFT JOIN khác nhau thế nào? Cho ví dụ khi nào bắt buộc dùng LEFT JOIN. A: INNER JOIN chỉ trả các dòng khớp ở cả hai bảng. LEFT JOIN giữ mọi dòng của bảng trái, bảng phải không khớp thì cột thành NULL.
