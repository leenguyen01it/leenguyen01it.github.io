1. JavaScript nâng cao và TypeScript

Đây là phần nền của cả backend lẫn frontend. Rất nhiều buổi phỏng vấn Middle mở đầu bằng 10–15 phút hỏi JavaScript core.

1.1. Scope, closure, hoisting Bắt buộc

  • var / let / const: var có function scope và được hoisting với giá trị undefined. let/const có block scope và nằm trong Temporal Dead Zone cho đến dòng khai báo.
  • Closure: hàm "nhớ" các biến của scope nơi nó được tạo ra, kể cả khi scope đó đã chạy xong. Ứng dụng: đóng gói dữ liệu, factory function, memoize, debounce.
js
// Câu hỏi kinh điển: in ra gì?
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i), 0); // 3 3 3
for (let j = 0; j < 3; j++) setTimeout(() => console.log(j), 0); // 0 1 2
// let tạo một biến j mới cho mỗi vòng lặp; var dùng chung một biến i.

// Closure: bộ đếm có dữ liệu "private"
function createCounter() {
  let count = 0;
  return { inc: () => ++count, get: () => count };
}
const c = createCounter();
c.inc(); c.inc();
console.log(c.get()); // 2

1.2. this, prototype, class Bắt buộc

  • this được xác định lúc gọi hàm, không phải lúc khai báo: obj.fn() thì this = obj. Gọi hàm rời (fn()) thì this là undefined trong strict mode.
  • Arrow function không có this riêng mà lấy this của scope bao ngoài. Vì vậy không nên dùng arrow function làm method của object.
  • call/apply gọi hàm với this chỉ định; bind trả về một hàm mới đã gắn cố định this.
  • class chỉ là cú pháp đẹp hơn cho prototype. Mỗi object có [[Prototype]]; khi tìm thuộc tính, JS đi ngược lên chuỗi prototype.

1.3. Kiểu dữ liệu, so sánh, sao chép Bắt buộc

  • 7 kiểu nguyên thủy (string, number, bigint, boolean, undefined, null, symbol) được truyền theo giá trị. Object, array, function được truyền theo tham chiếu.
  • Luôn dùng ===. Cần biết == có ép kiểu (0 == '' cho kết quả true).
  • Shallow copy: {...obj}, [...arr], Object.assign. Deep copy: structuredClone(obj). Cách JSON.parse(JSON.stringify()) làm mất Date, Map, undefined, function.
  • ?? khác ||: ?? chỉ thay khi giá trị là null/undefined, còn || thay cả với 0, '', false.
  • Cấu trúc dữ liệu: Map (key là kiểu bất kỳ, giữ thứ tự), Set (loại trùng), WeakMap (key là object, không chặn garbage collection).

1.5. Hàm bậc cao và các mẫu hay hỏi Bắt buộc

Bạn cần dùng thành thạo map, filter, reduce, some, every, find, flatMap, destructuring, rest/spread và optional chaining ?.. Hai bài code hay bị yêu cầu viết tay:

js
// Debounce: chỉ chạy sau khi người dùng ngừng gõ `ms` mili giây (ô tìm kiếm)
function debounce(fn, ms) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
}

// Throttle: chạy tối đa 1 lần mỗi `ms` mili giây (sự kiện scroll, resize)
function throttle(fn, ms) {
  let last = 0;
  return (...args) => {
    const now = Date.now();
    if (now - last >= ms) { last = now; fn(...args); }
  };
}

1.6. TypeScript Bắt buộc

Ở mức Middle, hầu hết JD (mô tả công việc) đều ghi TypeScript là yêu cầu bắt buộc. Bạn cần biết:

  • Kiểu cơ bản, type và interface: interface có thể mở rộng/gộp khai báo, phù hợp mô tả object; type dùng được cho union, tuple và mapped type.
  • Union và narrowing: thu hẹp kiểu bằng typeof, in, instanceof, hoặc type guard tự viết.
  • Generics: viết hàm/kiểu dùng lại được mà vẫn giữ đúng kiểu dữ liệu.
  • Utility types: Partial, Required, Pick, Omit, Record, ReturnType, Awaited.
  • unknown và any: unknown buộc phải kiểm tra kiểu trước khi dùng nên an toàn hơn. Nên tránh any.
  • never dùng để kiểm tra đã xử lý hết mọi trường hợp; satisfies kiểm tra kiểu mà không làm mất kiểu cụ thể.
  • Bật "strict": true trong tsconfig.json.
ts
// Discriminated union + kiểm tra đã xử lý hết trường hợp
type ApiResult<T> =
  | { status: 'success'; data: T }
  | { status: 'error'; message: string };

function render<T>(r: ApiResult<T>) {
  switch (r.status) {
    case 'success': return r.data;      // TS biết r có data
    case 'error':   return r.message;   // TS biết r có message
    default: { const _never: never = r; return _never; } // thêm status mới mà quên xử lý → báo lỗi
  }
}

// Generic có ràng buộc
function pluck<T, K extends keyof T>(items: T[], key: K): T[K][] {
  return items.map((i) => i[key]);
}

// Utility types cho DTO
interface User { id: number; email: string; password: string; createdAt: Date }
type PublicUser = Omit<User, 'password'>;
type UpdateUserDto = Partial<Pick<User, 'email' | 'password'>>;

Câu hỏi ôn tập

Tự trả lời thành tiếng trước, rồi bấm vào câu hỏi để xem gợi ý.

1. Closure là gì? Cho một ví dụ dùng closure trong dự án thật.

Closure là một hàm cùng với các biến của scope nơi hàm đó được tạo ra. Hàm vẫn dùng được các biến này dù scope bên ngoài đã chạy xong. Ví dụ trong dự án: middleware factory requireRole('admin') trả về một middleware nhớ được role; hàm debounce nhớ timer; module giữ biến private.

2. Khác nhau giữa var, let, const?

var có function scope, được hoisting với giá trị undefined và khai báo lại được. let và const có block scope và nằm trong TDZ trước dòng khai báo. const không gán lại được, nhưng object khai báo bằng const vẫn sửa được nội dung bên trong.

3. Arrow function khác function thường ở điểm nào?

Arrow function không có this, arguments và prototype riêng, nên không dùng làm constructor với new được. this của nó lấy từ scope bao ngoài, vì thế rất tiện cho callback trong method, nhưng không nên dùng làm method của object.

4. Promise.all và Promise.allSettled khác nhau thế nào? Khi nào dùng cái nào?

all reject ngay khi có một promise lỗi, nên hợp với các việc mà thiếu một cái là cả kết quả vô nghĩa. allSettled chờ tất cả chạy xong và trả về trạng thái của từng cái, nên hợp với các việc độc lập như gửi thông báo hàng loạt, cái nào lỗi thì ghi log cái đó.

5. Vì sao await bên trong forEach không hoạt động như mong đợi?

forEach không quan tâm promise mà callback trả về, nên nó gọi hết các callback rồi kết thúc ngay. Muốn chạy tuần tự thì dùng for...of; muốn chạy song song thì dùng Promise.all(arr.map(...)).

6. Deep copy một object thế nào? JSON.parse(JSON.stringify()) có vấn đề gì?

Dùng structuredClone. Cách JSON làm mất undefined, function và Symbol, biến Date thành string, không giữ được Map/Set, và báo lỗi khi gặp tham chiếu vòng.

7. interface và type trong TypeScript khác nhau ra sao?

Cả hai đều mô tả được object. interface có thể gộp khai báo (declaration merging) và extends, phù hợp cho kiểu public hoặc kiểu cần mở rộng. type dùng được cho union, tuple, mapped type và conditional type. Trong một dự án nên thống nhất một quy ước.

8. unknown khác any thế nào?

any tắt kiểm tra kiểu hoàn toàn. unknown nhận mọi giá trị nhưng bắt buộc phải thu hẹp kiểu (typeof, kiểm tra bằng zod) trước khi dùng. Vì vậy dữ liệu từ bên ngoài như body request hay JSON.parse nên khai báo là unknown.

Câu 1. Đoạn for (var i = 0; i < 3; i++) setTimeout(() => console.log(i)) in ra gì?

Đáp án D. var chỉ có một biến i dùng chung cho cả vòng lặp. Khi các callback chạy thì vòng lặp đã xong và i = 3.

Câu 2. Giá trị của 0 ?? 5 và 0 || 5 lần lượt là?

Đáp án C. ?? chỉ thay thế khi giá trị là null/undefined; || thay thế cả với mọi giá trị falsy, kể cả 0.

Câu 3. Promise nào reject chỉ khi TẤT CẢ các promise con đều lỗi?

Đáp án A. any resolve với promise thành công đầu tiên; chỉ khi tất cả đều lỗi mới reject với AggregateError.

Câu 4. Trong strict mode, const f = obj.method; f(); thì this bên trong là gì?

Đáp án D. this được xác định lúc gọi hàm. Gọi hàm rời không qua object thì this là undefined trong strict mode (ES module và class luôn ở strict mode).

Câu 5. Utility type nào tạo kiểu mà mọi thuộc tính đều không bắt buộc?

Đáp án C. Partial<T> thêm ? cho mọi thuộc tính, rất hay dùng cho DTO cập nhật (PATCH).

Câu 6. Có 3 lời gọi API độc lập, mỗi cái mất 1 giây. Cách nào nhanh nhất?

Đáp án A. Promise.all chạy song song nên mất khoảng 1 giây. Ba lệnh await nối tiếp mất 3 giây; forEach không chờ nên không có kết quả để dùng.

Câu 7. Tình huống nào nên dùng debounce thay vì throttle?

Đáp án A. Debounce chờ một khoảng "yên lặng" rồi mới chạy một lần. Throttle giới hạn số lần chạy trong khoảng thời gian, hợp với sự kiện liên tục như scroll.

Câu 8. Từ khóa never trong TypeScript thường dùng để làm gì?

Đáp án A. Gán biến đã thu hẹp hết vào kiểu never khiến TS báo lỗi khi union có thêm thành viên mà switch chưa xử lý.

2. Node.js core

Đây là phần phân biệt rõ nhất giữa người "biết dùng Express" và một Middle thực thụ.

2.1. Kiến trúc và event loop Bắt buộc

Node.js = engine V8 (chạy JS) + libuv (event loop, I/O bất đồng bộ). Code JS của bạn chạy trên một luồng. Network I/O dùng cơ chế bất đồng bộ của hệ điều hành (epoll, kqueue). Một số việc như fs, dns.lookup, crypto.pbkdf2, zlib chạy trên thread pool của libuv (mặc định 4 luồng, đổi bằng UV_THREADPOOL_SIZE).

process.nextTick(() => console.log('nextTick'));
console.log('2');
// Kết quả: 1, 2, nextTick, promise, rồi timeout/immediate (thứ tự 2 cái cuối KHÔNG cố định)

2.3. Stream và Buffer Nên biết

  • 4 loại stream: Readable (đọc file, request), Writable (ghi file, response), Duplex (socket), Transform (nén, mã hóa).
  • Backpressure: khi bên ghi chậm hơn bên đọc, stream tạm dừng việc đọc để RAM không bị đầy. Hàm pipeline xử lý việc này và cả lỗi cho bạn.
  • Buffer là dữ liệu nhị phân. Dùng khi xử lý file, ảnh, mã hóa.
js
import { createReadStream, createWriteStream } from 'node:fs';
import { createGzip } from 'node:zlib';
import { pipeline } from 'node:stream/promises';

// Nén file 5 GB mà chỉ tốn vài MB RAM
await pipeline(createReadStream('big.log'), createGzip(), createWriteStream('big.log.gz'));

// Express: trả file CSV lớn theo dạng stream thay vì đọc hết vào RAM
app.get('/export', (req, res) => {
  res.setHeader('Content-Type', 'text/csv');
  createReadStream('report.csv').pipe(res);
});

2.4. Xử lý lỗi Bắt buộc

  • Phân biệt lỗi vận hành (DB mất kết nối, input sai, gọi API timeout): bắt lỗi và trả về response phù hợp. Còn lỗi lập trình (bug, undefined is not a function): ghi log và để process khởi động lại.
  • Tự tạo class lỗi có statusCode, rồi xử lý tập trung ở một middleware.
  • Từ Node 15, một unhandledRejection sẽ làm process tắt. Hãy ghi log trong process.on('unhandledRejection') và uncaughtException, rồi thoát để PM2/Docker khởi động lại.

2.5. Tận dụng nhiều nhân CPU Nên biết

  • Cluster / PM2 (pm2 start app.js -i max): chạy nhiều process, mỗi process một nhân CPU, dùng chung một port. Các process không chia sẻ bộ nhớ, nên session và cache phải để trong Redis.
  • worker_threads: luồng riêng cho tác vụ nặng CPU (xử lý ảnh, tạo PDF, mã hóa), không làm chặn event loop chính.
  • child_process: chạy chương trình bên ngoài (ffmpeg, script Python).
  • Trong Kubernetes thường chạy mỗi container một process và scale bằng số lượng pod.

2.6. EventEmitter, cấu hình, hiệu năng Nên biết

  • EventEmitter: nền tảng của stream, server, socket. Nhớ gỡ listener (off) để tránh rò rỉ bộ nhớ.
  • Cấu hình: đọc từ biến môi trường và validate ngay khi khởi động. Thiếu biến thì báo lỗi ngay, không để đến lúc chạy mới lỗi.
  • Rò rỉ bộ nhớ hay gặp: cache trong biến global không giới hạn kích thước, listener không được gỡ, closure giữ object lớn, setInterval không được clear.
  • Công cụ: node --inspect + Chrome DevTools (heap snapshot, CPU profile), clinic.js, autocannon để load test.
  • Node bản mới có sẵn nhiều thứ: fetch, node --watch, node --env-file=.env, test runner node:test, chạy trực tiếp file .ts (type stripping).

Câu hỏi ôn tập

Tự trả lời thành tiếng trước, rồi bấm vào câu hỏi để xem gợi ý.

1. Node.js là đơn luồng, vậy sao xử lý được hàng nghìn request cùng lúc?

Chỉ phần chạy code JS là đơn luồng. I/O như mạng, file hay DB được giao cho hệ điều hành hoặc thread pool của libuv. Trong lúc chờ I/O, event loop tiếp tục nhận request khác; khi I/O xong thì callback được đưa vào hàng đợi để chạy. Mô hình này rất hợp với ứng dụng nhiều I/O, nhưng không hợp với việc nặng CPU.

2. Kể các pha của event loop. process.nextTick và Promise chạy lúc nào?

Các pha là timers → pending callbacks → (idle/prepare) → poll → check → close callbacks. Sau mỗi callback, Node chạy hết hàng đợi nextTick, rồi đến hết hàng đợi microtask của Promise, sau đó mới sang callback hoặc pha tiếp theo.

3. setImmediate khác setTimeout(fn, 0) thế nào?

setImmediate chạy ở pha check, ngay sau pha poll. setTimeout 0 chạy ở pha timers. Trong code chính, thứ tự hai cái không cố định; trong callback I/O thì setImmediate luôn chạy trước.

4. Làm sao biết event loop đang bị chặn và xử lý thế nào?

Dấu hiệu là latency tăng đều ở mọi endpoint và CPU 100% trên một nhân. Đo bằng perf_hooks.monitorEventLoopDelay hoặc clinic.js, tìm hàm nóng bằng CPU profile. Cách xử lý: dùng hàm async thay hàm sync, chuyển việc nặng sang worker_threads hoặc hàng đợi, dùng stream cho dữ liệu lớn, sửa regex dễ bị ReDoS.

5. Backpressure là gì?

Là khi bên nhận dữ liệu (Writable) xử lý chậm hơn bên gửi (Readable). write() trả về false thì bên gửi phải dừng lại cho đến khi có sự kiện drain. pipe và pipeline tự xử lý việc này, nhờ vậy RAM không bị đầy.

6. Cluster và worker_threads khác nhau thế nào?

Cluster tạo nhiều process, mỗi cái có bộ nhớ và event loop riêng, dùng chung port, dùng để scale khả năng xử lý request HTTP. worker_threads là các luồng trong cùng một process, có thể chia sẻ bộ nhớ (SharedArrayBuffer), dùng cho tác vụ nặng CPU.

7. Khi gặp uncaughtException có nên để app chạy tiếp không?

Không nên. Lúc đó trạng thái của app có thể đã hỏng. Đúng cách là ghi log, đóng kết nối một cách êm (graceful shutdown) rồi thoát process; PM2, Docker hoặc Kubernetes sẽ khởi động lại.

8. Những nguyên nhân phổ biến gây rò rỉ bộ nhớ trong Node?

Cache bằng object/Map global mà không giới hạn hay đặt TTL; thêm event listener mà không gỡ; setInterval không clear; closure giữ tham chiếu tới object lớn; mảng log tăng mãi. Cách tìm: chụp 2–3 heap snapshot cách nhau rồi so sánh xem object nào tăng lên.

3.1. Express Bắt buộc

  • Middleware là hàm (req, res, next), chạy theo đúng thứ tự khai báo. Middleware hoặc gửi response, hoặc gọi next() để chuyển tiếp.
  • Error middleware có 4 tham số (err, req, res, next) và đặt ở cuối cùng. Từ Express 5, lỗi trong hàm async tự động được chuyển tới middleware này mà không cần try/catch.
  • express.Router() chia route theo module. Đặt helmet, cors, express.json({ limit }) và rate limit ở đầu.

ts
import { randomUUID } from 'node:crypto';

// Gắn requestId và đo thời gian xử lý cho mọi request
export function requestContext(req, res, next) {
  req.id = req.get('x-request-id') ?? randomUUID();
  res.setHeader('x-request-id', req.id);
  const start = process.hrtime.bigint();
  res.on('finish', () => {
    const ms = Number(process.hrtime.bigint() - start) / 1e6;
    req.log?.info({ status: res.statusCode, ms }, `${req.method} ${req.originalUrl}`);
  });
  next();
}

Xử lý lỗi async: Express 4 và Express 5

Ở Express 4, lỗi trong hàm async không được chuyển tới error handler: request bị treo và xuất hiện cảnh báo unhandled rejection. Phải bọc lại bằng một wrapper hoặc dùng gói express-async-errors. Ở Express 5, promise bị reject sẽ tự động được chuyển thành next(err).

ts
// Express 4: wrapper bắt buộc phải có

router.get('/:id', asyncHandler(async (req, res) => {
  res.json(await productService.findById(Number(req.params.id)));
}));

// Express 5: viết thẳng, lỗi tự tới error handler
router.get('/:id', async (req, res) => {
  res.json(await productService.findById(Number(req.params.id)));
});

Những thay đổi khác của Express 5 cần biết khi nâng cấp: cú pháp đường dẫn mới (wildcard phải có tên, ví dụ /files/*path; tham số tùy chọn viết là /:file{.:ext}), req.query chỉ đọc được chứ không gán lại được, bỏ các hàm cũ như app.del và res.sendfile, yêu cầu Node 18 trở lên.

@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}
  canActivate(ctx: ExecutionContext): boolean {
    const roles = this.reflector.getAllAndOverride<Role[]>('roles', [ctx.getHandler(), ctx.getClass()]);
    if (!roles) return true;                       // route không yêu cầu role
    const { user } = ctx.switchToHttp().getRequest();
    return roles.includes(user?.role);             // false → 403 Forbidden
  }
}

  }

  • Versioning: /api/v1/... là cách phổ biến nhất.

3.4. Validate input Bắt buộc

Không bao giờ tin dữ liệu từ client. Validate body, params và query ở ngay đầu vào: dùng zod với Express, class-validator với NestJS. Với zod, một schema cho bạn cả bước validate lẫn kiểu TypeScript.

ts
import { z } from 'zod';
const CreateUser = z.object({
  email: z.string().email(),
  password: z.string().min(8),
  age: z.coerce.number().int().min(16).optional(),
});
type CreateUser = z.infer<typeof CreateUser>; // kiểu TS sinh ra từ schema

const validate = (schema) => (req, res, next) => {
  const r = schema.safeParse(req.body);
  if (!r.success) return res.status(400).json({ code: 'VALIDATION_ERROR', details: r.error.issues });
  req.body = r.data; // dữ liệu đã được làm sạch, các trường lạ bị loại bỏ
  next();
};
router.post('/', validate(CreateUser), createUserHandler);

Câu hỏi ôn tập

Tự trả lời thành tiếng trước, rồi bấm vào câu hỏi để xem gợi ý.

1. Middleware trong Express hoạt động thế nào? Vì sao thứ tự khai báo lại quan trọng?

Express chạy middleware theo đúng thứ tự app.use hoặc thứ tự route. Mỗi middleware có thể sửa req/res, gửi response, hoặc gọi next() để chuyển tiếp. Ví dụ: nếu đặt express.json() sau router thì req.body sẽ là undefined; nếu error handler không nằm cuối thì nó không bắt được lỗi của các route khai báo sau.

2. Trình bày luồng xử lý một request trong NestJS.

Middleware → Guard (có được phép vào không?) → Interceptor (phần trước handler) → Pipe (validate/transform tham số) → Controller → Service → Interceptor (phần sau handler, ví dụ bọc response) → nếu có lỗi thì Exception Filter định dạng response lỗi.

3. PUT và PATCH khác nhau thế nào? Phương thức nào idempotent?

PUT gửi toàn bộ tài nguyên để thay thế, PATCH chỉ gửi các trường cần sửa. GET, PUT, DELETE (và HEAD, OPTIONS) là idempotent. POST không idempotent. PATCH tùy cách cài đặt: { "stock": 5 } thì idempotent, còn "tăng thêm 1" thì không.

4. 401 và 403 khác nhau ra sao?

401 là chưa xác thực: không có token, token sai hoặc đã hết hạn, client cần đăng nhập lại. 403 là đã biết bạn là ai nhưng bạn không có quyền với tài nguyên này.

5. Lưu JWT ở localStorage hay cookie? Vì sao?

localStorage bị JS đọc được, nên dính XSS là mất token. Cookie HttpOnly thì JS không đọc được, nhưng phải chống CSRF bằng SameSite=Lax/Strict hoặc CSRF token. Cách hay dùng: access token ngắn hạn giữ trong bộ nhớ (biến JS), refresh token để trong cookie HttpOnly, Secure, SameSite.

6. Làm sao thu hồi JWT trước khi nó hết hạn?

Để access token sống ngắn (5–15 phút) rồi thu hồi refresh token trong DB. Nếu cần chặn ngay thì giữ blacklist jti trong Redis cho đến khi token hết hạn, hoặc lưu tokenVersion của user và tăng giá trị đó khi đăng xuất khỏi mọi thiết bị.

7. Vì sao cursor pagination nhanh hơn offset với bảng lớn?

OFFSET 100000 buộc DB đọc rồi bỏ đi 100.000 dòng. Cursor dùng WHERE (created_at, id) < (...), đi thẳng vào index nên tốc độ không phụ thuộc trang thứ mấy. Thêm nữa, khi có dòng mới được chèn vào thì cursor không bị trùng hay sót dữ liệu.

8. Khi nào nên dùng hàng đợi thay vì xử lý ngay trong request?

Khi việc đó chậm (gửi email, xuất file, xử lý ảnh), có thể lỗi và cần thử lại (gọi API bên thứ ba), cần lên lịch, hoặc cần giới hạn tốc độ. Request chỉ đẩy job vào hàng đợi rồi trả 202 hoặc 201 ngay, worker sẽ xử lý sau.

9. Graceful shutdown là gì và vì sao cần?

Khi deploy, Kubernetes hoặc Docker gửi tín hiệu SIGTERM. App cần ngừng nhận request mới, chạy nốt request đang dở, đóng kết nối DB/Redis rồi mới thoát. Không làm vậy thì người dùng bị lỗi 502 giữa chừng và có thể hỏng dữ liệu.

10. Express 4 và Express 5 xử lý lỗi trong hàm async khác nhau thế nào?

Express 4 không bắt promise bị reject: request bị treo và xuất hiện unhandled rejection, nên phải bọc handler bằng asyncHandler (.catch(next)) hoặc dùng express-async-errors. Express 5 tự chuyển promise bị reject thành next(err), nên có thể viết thẳng async (req, res) => {...}.

11. Vì sao nên tách hàm createApp() khỏi lệnh listen()?

Để test (Supertest) dùng được app mà không cần mở port thật, và để chạy cùng một app ở nhiều môi trường (server, serverless, test). File server.ts chỉ làm nhiệm vụ tạo app và listen.

12. res.locals dùng để làm gì?

Là nơi lưu dữ liệu trong phạm vi một request, dùng chung giữa các middleware, ví dụ user đã xác thực, requestId hay kết quả đã tính trước. Dữ liệu này hết hiệu lực khi request kết thúc.

13. Lỗi "Nest can't resolve dependencies of X" nghĩa là gì và sửa thế nào?

Nest không tìm thấy provider mà X cần inject. Nguyên nhân thường gặp: provider chưa nằm trong providers của module; module chứa nó chưa exports provider đó; module hiện tại chưa imports module kia; hoặc có phụ thuộc vòng (cần forwardRef).

14. Provider trong NestJS mặc định có scope gì? Điều đó ảnh hưởng gì khi viết service?

Mặc định là singleton, một instance dùng chung cho toàn app. Vì vậy không được lưu dữ liệu riêng của request (user hiện tại, giỏ hàng) trong thuộc tính của service, nếu không các request sẽ ghi đè lẫn nhau. Muốn có dữ liệu theo request thì truyền qua tham số, dùng Scope.REQUEST hoặc AsyncLocalStorage (nestjs-cls).

15. ValidationPipe với whitelist, forbidNonWhitelisted, transform có tác dụng gì?

whitelist bỏ các trường không khai báo trong DTO, giúp chống mass assignment. forbidNonWhitelisted báo lỗi 400 thay vì âm thầm bỏ trường lạ. transform biến plain object thành instance của DTO và ép kiểu (string sang number cho param và query).

16. Làm sao viết phân quyền theo role trong NestJS?

Tạo decorator @Roles(...) bằng SetMetadata; viết RolesGuard đọc metadata đó qua Reflector.getAllAndOverride (cấp handler và class), rồi so với req.user.role (đã được JwtAuthGuard gắn vào). Áp guard bằng @UseGuards hoặc toàn cục qua APP_GUARD.

17. Interceptor trong NestJS khác middleware ở điểm nào?

Middleware chạy trước khi Nest chọn route, không biết handler nào sẽ xử lý và không can thiệp được response trả về. Interceptor biết ExecutionContext (class, handler, metadata), bọc được cả phần trước và sau handler qua RxJS (map, tap, catchError), nên dùng được để định dạng response, cache, đo thời gian hay đặt timeout.

4. GraphQL

GraphQL là một ngôn ngữ truy vấn cho API: client mô tả chính xác dữ liệu cần lấy, server trả về đúng như vậy qua một endpoint duy nhất (POST /graphql). Nó hay gặp ở các sản phẩm có nhiều client (web, mobile) và dữ liệu lồng nhau phức tạp.

4.1. Khái niệm cốt lõi Bắt buộc

  • Schema (SDL): khai báo kiểu dữ liệu và các thao tác. Đây là "hợp đồng" giữa frontend và backend.

4.2. Bài toán N+1 và DataLoader Bắt buộc

Đây là câu hỏi GraphQL hay gặp nhất. Query 20 bài viết kèm author thì resolver Post.author chạy 20 lần, tức 1 query lấy bài viết + 20 query lấy user. DataLoader gom các id trong cùng một tick thành một query WHERE id IN (...) và cache kết quả trong phạm vi request đó.

ts
import DataLoader from 'dataloader';

// Tạo DataLoader MỚI cho mỗi request (trong context), để không lẫn cache giữa các user
const createLoaders = () => ({
  userById: new DataLoader(async (ids: readonly string[]) => {
    const users = await prisma.user.findMany({ where: { id: { in: [...ids] } } });
    const map = new Map(users.map((u) => [u.id, u]));
    return ids.map((id) => map.get(id) ?? null); // PHẢI trả về đúng thứ tự của ids
  }),
});

const resolvers = {
  Query: {

4.4. Bảo mật, phân trang, công cụ Nên biết

  • Chống query độc hại: giới hạn độ sâu (depth limit), giới hạn độ phức tạp (cost/complexity), giới hạn số phần tử mỗi trang, đặt timeout. Với app nội bộ thì chỉ cho chạy các query đã đăng ký trước (persisted queries).
  • Phân quyền đặt ở tầng resolver/service, kể cả với field lồng nhau (ví dụ User.email chỉ chủ tài khoản mới xem được).
  • Phân trang: chuẩn Relay Connection gồm edges { node cursor } và pageInfo { hasNextPage endCursor }, tức cursor-based.
  • Server: Apollo Server, GraphQL Yoga, hoặc @nestjs/graphql với hai cách: code-first (sinh schema từ decorator TS) hoặc schema-first.
  • Client: Apollo Client (có cache chuẩn hóa theo __typename + id), urql, hoặc TanStack Query kết hợp graphql-request.
  • Điểm cộng Federation: gộp schema của nhiều microservice thành một graph chung qua gateway (Apollo Router). Xem thêm phần Microservices.

Câu hỏi ôn tập

Tự trả lời thành tiếng trước, rồi bấm vào câu hỏi để xem gợi ý.

1. GraphQL giải quyết vấn đề gì của REST?

Over-fetching (lấy thừa field), under-fetching (phải gọi nhiều endpoint mới đủ dữ liệu cho một màn hình), và việc phải tạo thêm endpoint riêng cho từng loại client. Với GraphQL, client chọn đúng field cần, lấy dữ liệu lồng nhau trong một request, và có schema định kiểu sẵn.

2. Bài toán N+1 trong GraphQL là gì và giải quyết thế nào?

Mỗi phần tử trong danh sách gọi resolver con, và resolver đó lại query DB riêng, nên tổng cộng thành 1 + N query. Giải quyết bằng DataLoader: gom các key trong cùng một tick thành một query batch (IN (...)) và cache trong phạm vi request. Mỗi request phải tạo DataLoader mới.

3. Một resolver nhận những tham số nào?

parent là kết quả của field cha, args là tham số của field, context là dữ liệu dùng chung cho cả request (user, loaders, db), info là thông tin về AST của query (ít khi dùng).

4. Vì sao cache với GraphQL khó hơn với REST?

Mọi request thường là POST tới cùng một URL, nên cache HTTP và CDN không dùng được như với REST. Cách xử lý: cache chuẩn hóa ở client (Apollo), persisted query kèm GET để cache trên CDN, hoặc cache ở tầng resolver/DataLoader/Redis.

5. Làm sao bảo vệ server GraphQL khỏi query quá nặng?

Giới hạn độ sâu, tính điểm độ phức tạp, giới hạn first/limit, đặt timeout, rate limit theo user. Với client của chính mình thì dùng persisted query (allowlist). Có thể tắt introspection ở môi trường production.

6. GraphQL trả lỗi như thế nào?

Thường HTTP vẫn là 200, kèm mảng errors (gồm message, path, extensions.code). Một response có thể vừa có data vừa có errors nếu chỉ một vài field bị lỗi. Hãy dùng extensions.code (UNAUTHENTICATED, FORBIDDEN, BAD_USER_INPUT) để client xử lý.

7. Code-first và schema-first khác nhau thế nào?

Schema-first viết SDL trước rồi viết resolver theo đó. Code-first viết class TS có decorator (NestJS) rồi sinh ra SDL, nhờ vậy kiểu TS và schema không bao giờ lệch nhau.

5.1. SQL và thiết kế schema Bắt buộc

  • JOIN: INNER (chỉ dòng khớp ở cả hai bảng), LEFT (giữ mọi dòng bảng trái), RIGHT, FULL. GROUP BY + HAVING, subquery, CTE (WITH), window function (ROW_NUMBER() OVER (PARTITION BY ...)).

  • Xóa mềm (deleted_at), cột created_at/updated_at, nên dùng UUID hay số tự tăng.

5.2. Index và tối ưu query Bắt buộc

  • Index mặc định là B-tree, dùng tốt cho =, <, >, BETWEEN, ORDER BY và LIKE 'abc%'. Nó không giúp được LIKE '%abc', hay khi bọc cột trong hàm (WHERE LOWER(email) = ..., trừ khi tạo index theo biểu thức).
  • Composite index (a, b, c) theo quy tắc leftmost prefix: dùng được cho điều kiện trên a, a,b, a,b,c, nhưng không dùng được khi chỉ lọc theo b. Nên đặt cột lọc bằng = trước, cột lọc theo khoảng hoặc sắp xếp sau.
  • Covering index: index chứa đủ mọi cột mà query cần, nên DB không phải đọc bảng.
  • Index giúp đọc nhanh nhưng làm chậm việc ghi và tốn dung lượng. Đừng đánh index mọi cột.
  • Đọc EXPLAIN ANALYZE: Seq Scan trên bảng lớn là dấu hiệu xấu; số dòng ước lượng lệch nhiều so với thực tế thì cần chạy ANALYZE để cập nhật thống kê.
  • Lỗi N+1 với ORM: lặp qua danh sách đơn hàng rồi query user cho từng đơn. Sửa bằng include/JOIN (giống with() trong Eloquent).
  • Dùng connection pool, đặt giới hạn số kết nối hợp lý (max), và không mở kết nối mới cho mỗi request.

5.6. Redis và cache Bắt buộc

  • Kiểu dữ liệu: String, Hash, List, Set, Sorted Set (bảng xếp hạng), Stream. Mọi lệnh đều là nguyên tử vì Redis thực thi lệnh trên một luồng.
  • Dùng cho: cache, session, rate limit, hàng đợi (BullMQ), pub/sub, khóa phân tán, đếm lượt xem.
  • Cache-aside (phổ biến nhất): đọc cache, không có thì đọc DB rồi ghi vào cache kèm TTL. Khi ghi dữ liệu thì xóa key cache thay vì cập nhật nó.
  • Các vấn đề cần biết: cache stampede (key hot hết hạn, nghìn request cùng đập vào DB; xử lý bằng lock hoặc làm mới sớm), cache penetration (query key không tồn tại liên tục; cache cả giá trị null), nhiều key hết hạn cùng lúc (thêm độ lệch ngẫu nhiên cho TTL).
ts
async function getProduct(id: number) {
  const key = `product:${id}`;
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);

  const product = await prisma.product.findUnique({ where: { id } });
  const ttl = 300 + Math.floor(Math.random() * 60);        // 5–6 phút, lệch ngẫu nhiên
  await redis.set(key, JSON.stringify(product ?? null), 'EX', product ? ttl : 30);
  return product;
}
async function updateProduct(id: number, data) {
  const p = await prisma.product.update({ where: { id }, data });
  await redis.del(`product:${id}`);                         // xóa cache sau khi ghi DB
  return p;
}

// Rate limit fixed window: tối đa 100 request/phút cho mỗi IP
async function rateLimit(ip: string) {
  const key = `rl:${ip}:${Math.floor(Date.now() / 60000)}`;
  const n = await redis.incr(key);
  if (n === 1) await redis.expire(key, 60);
  return n <= 100;
}

Câu hỏi ôn tập

Tự trả lời thành tiếng trước, rồi bấm vào câu hỏi để xem gợi ý.

1. INNER JOIN và LEFT JOIN khác nhau thế nào? Cho ví dụ khi nào bắt buộc dùng LEFT JOIN.

INNER JOIN chỉ trả các dòng khớp ở cả hai bảng. LEFT JOIN giữ mọi dòng của bảng trái, bảng phải không khớp thì cột thành NULL. Ví dụ: liệt kê mọi user kèm số đơn hàng, kể cả user chưa có đơn nào: users LEFT JOIN orders rồi dùng COUNT(o.id).

2. Index hoạt động ra sao? Khi nào index không được dùng?

B-tree là cây đã sắp xếp, giúp tìm kiếm trong O(log n) thay vì quét cả bảng. Index không được dùng khi: bọc cột trong hàm, dùng LIKE '%x', không khớp leftmost prefix của composite index, ép kiểu ngầm, cột có độ chọn lọc thấp (ví dụ cột giới tính), hoặc bảng quá nhỏ khiến planner chọn quét cả bảng.

3. Có composite index (user_id, created_at). Query WHERE created_at > ... có dùng được index không?

Thường là không hiệu quả, vì nó vi phạm leftmost prefix: index được sắp theo user_id trước. Cần một index riêng trên created_at, hoặc thêm điều kiện user_id vào query.

4. Lỗi N+1 query là gì? Phát hiện và sửa thế nào?

Là khi lấy N bản ghi rồi chạy thêm một query cho từng bản ghi để lấy dữ liệu liên quan. Phát hiện bằng cách bật log query của ORM hoặc dùng APM thấy số query tăng theo số dòng. Sửa bằng eager loading (include trong Prisma, with() trong Laravel), JOIN, hoặc gom thành một query WHERE id IN (...).

5. Giải thích ACID và các isolation level.

ACID gồm Atomicity, Consistency, Isolation, Durability. Bốn mức isolation từ thấp đến cao: Read Uncommitted, Read Committed (mặc định của Postgres, chặn dirty read), Repeatable Read (mặc định của MySQL, chặn thêm non-repeatable read), Serializable (như chạy tuần tự, có thể phải retry khi xung đột). Mức càng cao thì càng an toàn nhưng càng chậm và càng dễ xung đột.

6. Hai request cùng trừ tồn kho của một sản phẩm. Làm sao để không bị bán âm?

Cách tốt nhất là UPDATE nguyên tử có điều kiện (SET stock = stock - 1 WHERE id = ? AND stock >= 1) rồi kiểm tra số dòng bị ảnh hưởng. Các cách khác: SELECT ... FOR UPDATE trong transaction (pessimistic lock), cột version (optimistic lock), hoặc khóa phân tán trong Redis nếu dữ liệu nằm ở nhiều hệ thống.

7. Khi nào chọn MongoDB thay vì PostgreSQL?

Khi dữ liệu dạng document có cấu trúc thay đổi nhiều (catalog sản phẩm nhiều loại thuộc tính, log, nội dung CMS), cần ghi nhiều và scale ngang dễ, và ít quan hệ hay transaction phức tạp. Dữ liệu tài chính, đơn hàng hay nhiều quan hệ thì nên dùng SQL. Postgres có JSONB nên cũng đáp ứng được phần lớn nhu cầu "linh hoạt".

8. Trình bày cache-aside và cách xử lý khi dữ liệu thay đổi.

Khi đọc: tìm trong cache, nếu không có thì đọc DB rồi ghi vào cache kèm TTL. Khi ghi: cập nhật DB trước rồi xóa key cache, lần đọc sau sẽ nạp dữ liệu mới. Nên xóa thay vì cập nhật cache để tránh ghi đè dữ liệu cũ khi có nhiều request cùng lúc. TTL là lớp bảo vệ cuối nếu có lần quên xóa cache.

9. Cache stampede là gì?

Một key rất "hot" hết hạn, hàng nghìn request cùng thấy cache trống và cùng query DB, khiến DB quá tải. Cách chống: chỉ một request được nạp lại dữ liệu (lock bằng SET NX), làm mới cache trước khi hết hạn, hoặc cho phép trả dữ liệu cũ trong lúc nạp mới (stale-while-revalidate).

6. React

Ở mức Middle, người phỏng vấn không hỏi "useState dùng thế nào" nữa. Họ hỏi vì sao component re-render, khi nào cần useMemo, và quản lý state ở đâu.

6.1. Cơ chế render Bắt buộc

  • Render phase: React gọi hàm component để tạo cây element mới, rồi so sánh với cây cũ (reconciliation). Commit phase: áp phần thay đổi vào DOM thật, sau đó chạy effect.
  • Component re-render khi: (1) state của nó thay đổi, (2) component cha re-render (dù props không đổi), (3) giá trị của Context mà nó dùng thay đổi. Re-render không có nghĩa là DOM thay đổi.
  • key giúp React biết phần tử nào là phần tử nào trong danh sách. Dùng id ổn định; dùng index làm key sẽ lỗi khi chèn, xóa hoặc sắp xếp lại (input giữ sai giá trị). Đổi key của một component thì component đó bị tạo mới hoàn toàn (đây cũng là một mẹo để reset state).
  • State là bất biến (immutable): luôn tạo object/array mới, không sửa trực tiếp. React so sánh bằng Object.is.
  • Batching: từ React 18, nhiều lệnh setState trong cùng một sự kiện (kể cả trong promise hay timeout) được gộp thành một lần render.

  const [v, setV] = useState(value);

  return v;

Custom hook mẫu

Custom hook dùng chung logic, không dùng chung state: mỗi component gọi hook sẽ có state riêng. Tên phải bắt đầu bằng use.

tsx
// Đóng popup khi click ra ngoài
function useOnClickOutside(ref: React.RefObject<HTMLElement>, handler: () => void) {
  useEffect(() => {
    const listener = (e: MouseEvent) => {
      if (!ref.current || ref.current.contains(e.target as Node)) return;
      handler();
    };
    document.addEventListener('mousedown', listener);
    return () => document.removeEventListener('mousedown', listener);
  }, [ref, handler]);
}

// Đồng bộ state với localStorage (an toàn khi trình duyệt chặn storage)
function useLocalStorage<T>(key: string, initial: T) {
  const [value, setValue] = useState<T>(() => {
    try { const raw = localStorage.getItem(key); return raw ? (JSON.parse(raw) as T) : initial; }
    catch { return initial; }
  });
  useEffect(() => { try { localStorage.setItem(key, JSON.stringify(value)); } catch {} }, [key, value]);
  return [value, setValue] as const;
}

6.3. Tối ưu hiệu năng Bắt buộc

  • Đo trước khi tối ưu: dùng React DevTools Profiler (bật "Highlight updates") để xem component nào render, render bao lâu và vì sao.
  • React.memo(Component) bỏ qua re-render nếu props không đổi (so sánh nông). Nó vô dụng nếu mỗi lần render cha lại truyền object hay hàm mới; khi đó cần useMemo/useCallback.
  • Đặt state gần nơi dùng nhất (state colocation). Truyền component con qua children để nó không re-render theo cha.
  • Context: tách thành nhiều context nhỏ, hoặc tách context chứa state và context chứa hàm dispatch, để tránh cả cây render lại.
  • Danh sách dài (hàng nghìn dòng): virtualization (TanStack Virtual, react-window).
  • Code splitting: React.lazy + Suspense để tải từng route khi cần.
  • React Compiler (bản ổn định từ cuối 2025) tự động memo hóa lúc build, nên dự án dùng nó sẽ ít phải viết useMemo/useCallback tay. Tuy vậy phỏng vấn vẫn hỏi nguyên lý.
tsx
const Row = memo(function Row({ item, onSelect }: { item: Item; onSelect: (id: string) => void }) {
  return <li onClick={() => onSelect(item.id)}>{item.name}</li>;
});

function List({ items, filter }: Props) {
  const [selected, setSelected] = useState<string | null>(null);
  const visible = useMemo(() => items.filter((i) => i.name.includes(filter)), [items, filter]);

  return <ul>{visible.map((i) => <Row key={i.id} item={i} onSelect={onSelect} />)}</ul>;
}

6.5. Form, routing, xử lý lỗi Bắt buộc

  • Controlled (giá trị nằm trong state, mỗi lần gõ là một lần render) và uncontrolled (DOM giữ giá trị, đọc qua ref). react-hook-form dùng uncontrolled nên nhanh với form lớn.
  • Dùng chung schema zod giữa frontend và backend (trong monorepo) để validate giống nhau ở cả hai đầu.
  • React Router: nested route, useParams, useSearchParams, route cần đăng nhập (protected route), loader/action (data router).
  • Error Boundary: bắt lỗi khi render của cây con và hiển thị giao diện dự phòng. Nó không bắt lỗi trong event handler hay code async (những chỗ đó phải tự try/catch).

6.6. React 19 Nên biết

  • Actions: truyền hàm async vào <form action={fn}>; React tự quản lý trạng thái pending và lỗi.

  • Server Actions ('use server'): hàm chạy trên server, gọi được từ form hoặc client. Nó vẫn là một endpoint công khai, nên phải tự kiểm tra auth và validate bên trong.
  • Ngoài ra cần biết: layout, loading, error, route handler (route.ts), middleware, next/image, và cơ chế cache/revalidate (cách cache mặc định đã thay đổi qua các phiên bản, nên đọc docs của bản bạn đang dùng).

Lấy dữ liệu, streaming và cache

  • Trong Server Component, gọi DB hoặc fetch trực tiếp bằng await; không cần useEffect hay API trung gian.
  • Các truy vấn độc lập nhau thì chạy song song bằng Promise.all. Phần nào chậm thì bọc trong <Suspense> để phần còn lại hiện trước (streaming).
  • Trang tĩnh hay động: trang tự trở thành động (render ở mỗi request) khi dùng cookies(), headers() hoặc searchParams. Từ Next 15, các API này và params đều là async (phải await).
  • Cache: từ Next 15, fetch không còn được cache mặc định. Muốn cache thì khai báo rõ: fetch(url, { next: { revalidate: 60, tags: ['products'] } }), hoặc export const revalidate = 60 ở cấp route.   • Làm mới cache sau khi ghi: revalidatePath('/products') hoặc revalidateTag('products').
  • generateStaticParams tạo sẵn trang cho các route động lúc build (SSG/ISR).

Câu hỏi ôn tập

Tự trả lời thành tiếng trước, rồi bấm vào câu hỏi để xem gợi ý.

1. Khi nào một component re-render?

Khi state của nó đổi, khi component cha re-render, hoặc khi giá trị Context mà nó dùng đổi. Props thay đổi không phải là nguyên nhân riêng biệt: props chỉ đổi khi cha render lại. Re-render là gọi lại hàm component; DOM chỉ cập nhật ở những chỗ có khác biệt.

2. Vì sao không nên dùng index làm key?

Khi chèn, xóa hoặc sắp xếp lại danh sách, index của các phần tử thay đổi, React ghép nhầm component với dữ liệu, nên state nội bộ (giá trị input, focus) bị gắn sai dòng và hiệu năng kém hơn. Index chỉ dùng được khi danh sách tĩnh, không bao giờ đổi thứ tự.

3. useMemo và useCallback khác nhau thế nào? Khi nào KHÔNG nên dùng?

useMemo nhớ giá trị trả về, useCallback nhớ chính hàm (tương đương useMemo(() => fn, deps)). Không nên dùng cho phép tính rẻ, hoặc khi bên nhận không được bọc memo và không đặt giá trị đó trong dependency, vì khi ấy chỉ tốn thêm chi phí so sánh mà không được gì. Hãy đo bằng Profiler trước.

4. Cleanup trong useEffect chạy khi nào? Cho ví dụ cần cleanup.

Cleanup chạy trước khi effect chạy lại (khi dependency đổi) và khi component unmount. Ví dụ: clearInterval, gỡ event listener, đóng WebSocket, abort fetch để tránh race condition và tránh cập nhật state sau khi đã unmount.

5. "Stale closure" trong React là gì?

Hàm như callback của effect hay setInterval giữ giá trị state tại thời điểm hàm được tạo, nên sau đó nó đọc phải giá trị cũ. Cách sửa: khai báo đủ dependency, dùng functional update setX(x => ...), hoặc lưu giá trị mới nhất vào useRef.

6. Phân biệt server state và client state. Vì sao không nên để dữ liệu API trong Redux?

Server state là bản sao của dữ liệu nằm trên server, có thể cũ, cần cache, refetch, chống request trùng và xử lý loading/error. Client state chỉ tồn tại ở trình duyệt. Để dữ liệu API trong Redux thì phải tự viết lại những gì TanStack Query đã có sẵn, nên code dài và dễ sai.

7. Context có vấn đề gì về hiệu năng? Cách khắc phục?

Khi value thay đổi (kể cả khi chỉ là object mới tạo lại mỗi lần render) thì mọi component dùng context đó đều render lại. Khắc phục: memo value, tách nhỏ context, tách context state và context dispatch, hoặc dùng Zustand để component chỉ subscribe phần dữ liệu mình cần.

8. Server Component và Client Component khác nhau thế nào?

Server Component chạy trên server, có thể async và truy cập DB/secret trực tiếp, không gửi JS của nó xuống client, nhưng không có state, effect hay event. Client Component có 'use client', có tương tác, và JS của nó được gửi về trình duyệt. Server Component có thể chứa Client Component; props truyền qua ranh giới đó phải serialize được.

9. SSR, SSG, ISR khác nhau và khi nào dùng?

SSR tạo HTML ở mỗi request, cho dữ liệu cá nhân hóa hoặc thay đổi liên tục. SSG tạo HTML lúc build, nhanh nhất, cho nội dung tĩnh. ISR là SSG nhưng tạo lại định kỳ hoặc khi được gọi, cho trang sản phẩm hay tin tức. Cả ba đều tốt cho SEO hơn CSR.

10. Vì sao truyền object làm dependency của useEffect dễ gây vòng lặp?

Object và hàm được tạo mới ở mỗi lần render, nên với Object.is chúng luôn "khác". Effect chạy sau mỗi lần render; nếu effect lại set state thì gây render mới, và cứ thế lặp vô hạn. Cách sửa: dùng giá trị nguyên thủy làm dependency, tạo object bên trong effect, hoặc memo hóa.

11. Khi nào dùng useReducer thay vì useState?

Khi state có nhiều trường liên quan với nhau, có nhiều loại hành động, giá trị mới phụ thuộc giá trị cũ theo logic phức tạp, hoặc muốn tách logic ra một hàm thuần để dễ test. dispatch có tham chiếu ổn định nên truyền xuống con không gây re-render thừa.

12. useTransition và useDeferredValue giải quyết vấn đề gì?

Cả hai đều giữ cho giao diện phản hồi nhanh khi có một phần render nặng. useTransition bọc lệnh cập nhật state "không gấp", nên React ưu tiên cập nhật gấp (gõ phím) trước. useDeferredValue cho bạn bản "trễ" của một giá trị để dùng ở phần render nặng. Cả hai đều có thể bị ngắt giữa chừng nếu có cập nhật mới hơn.

13. Vì sao custom hook useAuth nên ném lỗi khi context là null?

Để phát hiện ngay lỗi dùng hook ngoài Provider với thông báo rõ ràng, thay vì nhận về null rồi crash ở một chỗ khó hiểu. Kèm theo đó TypeScript có kiểu non-null, nên không cần kiểm tra ?. ở mọi nơi dùng.

14. Hai component cùng gọi một custom hook useCounter(). Chúng có dùng chung state không?

Không. Custom hook chỉ dùng chung logic; mỗi lần gọi tạo ra state riêng. Muốn dùng chung state thì phải nâng state lên cha, dùng Context, hoặc dùng store (Zustand).

15. layout.tsx và page.tsx trong Next.js khác nhau thế nào?

page.tsx là nội dung riêng của route. layout.tsx bao quanh page và các route con, được giữ lại (không render lại, không mất state) khi điều hướng giữa các trang con. Đặt header, sidebar, provider ở layout.

16. Trong Next.js 15+, làm sao để cache kết quả fetch và làm mới khi dữ liệu thay đổi?

Khai báo rõ fetch(url, { next: { revalidate: 60, tags: ['products'] } }) hoặc export const revalidate ở cấp route (từ Next 15, fetch không được cache mặc định). Sau khi ghi dữ liệu thì gọi revalidateTag('products') hoặc revalidatePath('/products') trong Server Action hoặc route handler.

17. Vì sao chỉ chặn đăng nhập ở middleware là chưa đủ?

Middleware chỉ chặn theo đường dẫn, có thể bị bỏ sót do cấu hình matcher, và không bảo vệ được Server Action (một endpoint POST gọi được trực tiếp) hay route handler. Phải kiểm tra quyền ngay tại nơi đọc/ghi dữ liệu: Server Component, Server Action, route handler, tầng data access.

18. Streaming với Suspense trong Next.js mang lại lợi ích gì?

Phần nhanh của trang (thông tin sản phẩm) được gửi và hiển thị ngay; phần chậm (đánh giá, gợi ý) hiện skeleton rồi được stream xuống khi xong. Nhờ vậy TTFB và LCP tốt hơn, người dùng không phải chờ truy vấn chậm nhất.

7. Nền tảng frontend và trình duyệt

7.1. HTML và CSS Bắt buộc

  • HTML semantic: header, nav, main, article, button (không dùng div onClick), label gắn với input. Tốt cho SEO và cho người dùng trình đọc màn hình.
  • Box model, box-sizing: border-box; position (relative, absolute, fixed, sticky), z-index và stacking context.
  • Flexbox cho bố cục một chiều (thanh menu, căn giữa); Grid cho bố cục hai chiều (lưới sản phẩm, layout trang).
  • Responsive: thiết kế mobile-first, media query, đơn vị rem/%/vw, clamp(); ảnh responsive dùng srcset.
  • Tailwind CSS rất phổ biến hiện nay. Ngoài ra nên biết CSS Modules và thư viện component (shadcn/ui, MUI, Ant Design).
  • Độ ưu tiên selector (specificity): inline > id > class/attribute/pseudo-class > element.

7.2. Trình duyệt hoạt động thế nào Bắt buộc

  1. Phân giải DNS → kết nối TCP + TLS → gửi request HTTP → nhận HTML.
  2. Phân tích HTML thành DOM, CSS thành CSSOM, ghép lại thành render tree → layout (tính vị trí) → paint (vẽ) → composite (ghép các lớp).
  3. Thẻ <script> thường chặn việc phân tích HTML. defer tải song song và chạy sau khi phân tích xong, giữ đúng thứ tự. async chạy ngay khi tải xong, không giữ thứ tự.
  4. Thay đổi kích thước hay vị trí gây reflow (tốn kém). Chỉ đổi màu thì gây repaint. Hiệu ứng chuyển động nên dùng transform/opacity để chỉ phải composite.

7.3. CORS, cookie, lưu trữ Bắt buộc

  • Same-origin policy: origin gồm giao thức + domain + port. Trình duyệt chặn JS đọc response từ origin khác, trừ khi server cho phép qua header Access-Control-Allow-Origin.
  • Preflight: với request "không đơn giản" (PUT, DELETE, PATCH, header tùy chỉnh như Authorization, Content-Type: application/json), trình duyệt gửi OPTIONS trước để hỏi.
  • Gửi cookie khác origin cần credentials: 'include' ở client và Access-Control-Allow-Credentials: true ở server. Khi đó Allow-Origin không được là *.
  • CORS là cơ chế của trình duyệt: Postman hay curl không bị chặn. Vì vậy CORS không thay thế được xác thực.

Tự trả lời thành tiếng trước, rồi bấm vào câu hỏi để xem gợi ý.

1. Trình bày điều gì xảy ra từ lúc gõ URL đến khi trang hiển thị.

Phân giải DNS ra IP → kết nối TCP và bắt tay TLS → gửi HTTP request (có thể qua CDN/proxy) → server trả HTML → trình duyệt phân tích HTML thành DOM, tải CSS/JS → tạo CSSOM → render tree → layout → paint → composite. Script không có defer chặn việc phân tích; CSS chặn việc render.

2. CORS là gì? Vì sao gọi API bằng Postman được mà từ trình duyệt thì lỗi?

CORS là cơ chế trình duyệt dùng để cho phép JS đọc response từ origin khác, dựa trên header mà server trả về. Postman không phải trình duyệt nên không áp dụng chính sách này. Cách sửa là cấu hình ở server (Access-Control-Allow-Origin đúng domain, methods, headers, credentials), không phải sửa ở frontend.

3. Preflight request là gì?

Là request OPTIONS mà trình duyệt tự gửi trước một request "không đơn giản" (method khác GET/POST/HEAD, có header tùy chỉnh, hoặc Content-Type là application/json) để hỏi server có cho phép không. Server trả về các header Allow-Methods/Allow-Headers; có thể cache kết quả bằng Access-Control-Max-Age.

4. SameSite của cookie có tác dụng gì?

Nó quy định cookie có được gửi kèm request từ trang khác không. Strict: không bao giờ. Lax (mặc định): chỉ gửi khi điều hướng cấp cao nhất bằng GET (bấm link). None: luôn gửi, bắt buộc kèm Secure. Lax/Strict chặn được phần lớn tấn công CSRF.

5. defer và async khác nhau thế nào?

Cả hai đều tải script song song với việc phân tích HTML. defer chạy sau khi phân tích xong và giữ đúng thứ tự các script, phù hợp cho script của app. async chạy ngay khi tải xong, không giữ thứ tự, phù hợp cho script độc lập như analytics.

6. Kể 3 chỉ số Core Web Vitals và một cách cải thiện mỗi chỉ số.

LCP ≤ 2,5 giây: tối ưu và preload ảnh hero, dùng SSR hoặc CDN. INP ≤ 200 ms: chia nhỏ task dài, giảm lượng JS và re-render. CLS ≤ 0,1: khai báo kích thước cho ảnh và iframe, chừa sẵn chỗ cho nội dung tải sau.

7. Flexbox và Grid khác nhau thế nào?

Flexbox sắp xếp theo một chiều (hàng hoặc cột), kích thước phụ thuộc nội dung, phù hợp cho thanh công cụ hay căn giữa. Grid sắp theo hai chiều (hàng và cột cùng lúc), phù hợp cho layout trang hay lưới thẻ. Hai cái thường được dùng kết hợp.

1. Unit test, integration test và E2E test khác nhau thế nào? Bạn viết loại nào nhiều nhất?

Unit test kiểm tra một hàm hoặc một class, phần phụ thuộc thì mock, chạy rất nhanh. Integration test kiểm tra nhiều thành phần chạy cùng nhau, ví dụ API với DB thật. E2E chạy trên trình duyệt thật theo luồng của người dùng. Theo kim tự tháp test thì unit test nhiều nhất; tuy vậy với API backend, integration test qua Supertest thường đem lại nhiều giá trị nhất.

2. Khi nào nên mock, khi nào không?

Nên mock những thứ chậm, không ổn định hoặc gây tác dụng phụ: API bên ngoài, email, thanh toán, thời gian, số ngẫu nhiên. Không nên mock chính thứ đang test, và với integration test thì hạn chế mock DB (dùng DB test trong Docker). Mock quá nhiều khiến test vẫn pass trong khi code thật đã hỏng.

3. Merge và rebase khác nhau thế nào? Khi nào không được rebase?

Merge tạo một merge commit và giữ nguyên lịch sử gốc. Rebase đặt lại các commit của bạn lên trên nhánh đích để lịch sử thẳng hàng, nhưng điều đó làm đổi hash của commit. Không rebase những nhánh đã push mà người khác đang làm việc trên đó.

4. Vì sao trong Dockerfile phải COPY package.json trước rồi mới COPY source?

Để tận dụng cache của layer. Khi chỉ sửa code mà không đổi dependency, layer npm ci được dùng lại nên build nhanh hơn rất nhiều.

5. Multi-stage build có lợi gì?

Image cuối cùng chỉ chứa code đã build và dependency để chạy, không có devDependencies, source TS hay công cụ build. Nhờ vậy image nhỏ hơn, deploy nhanh hơn và ít bề mặt tấn công hơn.

6. Trình bày XSS và cách React chống XSS.

XSS là khi kẻ tấn công chèn được script vào trang, script đó chạy trên trình duyệt nạn nhân và lấy cắp token hay thực hiện hành động thay họ. React tự escape mọi giá trị được render qua {}. Rủi ro còn lại nằm ở dangerouslySetInnerHTML, ở URL dạng javascript: trong href, và ở thư viện bên thứ ba. Biện pháp bổ sung: sanitize bằng DOMPurify, đặt header CSP, để token trong cookie HttpOnly.

7. CSRF là gì, và nếu dùng JWT trong header Authorization thì có bị CSRF không?

CSRF là khi trang web khác khiến trình duyệt của nạn nhân gửi request kèm cookie của họ tới site của bạn. Nếu token được gửi qua header Authorization (do JS gắn vào) thì trình duyệt không tự gửi, nên không bị CSRF. Ngược lại, khả năng bị XSS lấy token lại cao hơn. Nếu xác thực bằng cookie thì cần SameSite và/hoặc CSRF token.

8. Lỗi IDOR là gì?

Insecure Direct Object Reference: API chỉ kiểm tra là user đã đăng nhập, mà không kiểm tra tài nguyên có thuộc về user đó không. Kẻ tấn công chỉ cần đổi id trong URL. Phòng chống: luôn lọc theo chủ sở hữu hoặc kiểm tra policy ở tầng service.

9. Bạn quản lý secret (mật khẩu DB, API key) thế nào?

Để trong biến môi trường hoặc trình quản lý secret của nền tảng (GitHub Secrets, AWS Secrets Manager, Vault). Có file .env.example không chứa giá trị thật; .env nằm trong .gitignore. Không đóng gói secret vào image, không ghi secret ra log. Nếu lỡ lộ thì đổi (rotate) ngay.

9. System design cơ bản

Với vị trí Middle, câu hỏi system design thường ở mức "thiết kế một tính năng" hoặc "hệ thống nhỏ", hoặc chỉ là "app của bạn đang chậm, bạn làm gì?". Điều người phỏng vấn muốn thấy là bạn có cách tiếp cận bài bản và biết các đánh đổi, không phải đáp án hoàn hảo.

9.1. Cách trả lời một câu hỏi system design Nên biết

  1. Làm rõ yêu cầu (3–5 phút): có những chức năng nào, bao nhiêu người dùng, tỉ lệ đọc/ghi, yêu cầu về độ trễ, dữ liệu có cần nhất quán ngay không.
  2. Ước lượng: request/giây, dung lượng lưu trữ. Ví dụ 1 triệu user/ngày × 10 request = 10 triệu request/ngày, tức khoảng 120 request/giây trung bình, giờ cao điểm khoảng 5 lần.
  3. Thiết kế API và mô hình dữ liệu (bảng, index).
  4. Vẽ kiến trúc tổng thể như hình trên.
  5. Đi sâu vào điểm nghẽn: cache, index, hàng đợi, scale DB; nêu đánh đổi của từng lựa chọn.

9.3. Ba bài mẫu hay gặp Nên biết

a) Dịch vụ rút gọn link: POST /links trả về mã 7 ký tự; GET /:code redirect 302 (hoặc 301 nếu không cần đếm click). Mã được sinh bằng cách mã hóa base62 một id tự tăng (có thể dùng bộ đếm Redis INCR), hoặc sinh ngẫu nhiên rồi kiểm tra trùng. Tỉ lệ đọc rất cao so với ghi, nên cache code → url trong Redis. Đếm click không nên ghi DB ở mỗi request: tăng bộ đếm trong Redis rồi ghi dồn định kỳ, hoặc đẩy sự kiện vào hàng đợi.

b) Hệ thống thông báo (email, push, in-app): API nhận sự kiện → đẩy vào hàng đợi theo từng kênh → worker gửi, có retry + backoff, và dead-letter queue cho các lần lỗi cuối cùng. Cần lưu cài đặt của user (tắt kênh nào), chống gửi trùng bằng idempotency key, giới hạn tốc độ theo nhà cung cấp. Thông báo in-app realtime thì đẩy qua WebSocket/SSE.

c) Flash sale / đặt vé, chống bán vượt số lượng: trừ tồn kho bằng thao tác nguyên tử (DECR trong Redis hoặc UPDATE ... WHERE stock > 0), giữ chỗ có thời hạn (ví dụ 10 phút để thanh toán, hết hạn thì trả lại kho), cho người dùng xếp hàng chờ để chịu tải đột biến, rate limit theo user, và gửi kèm idempotency key khi tạo đơn.

Câu hỏi ôn tập

Tự trả lời thành tiếng trước, rồi bấm vào câu hỏi để xem gợi ý.

1. Ứng dụng của bạn đột nhiên chậm. Bạn điều tra thế nào?

(1) Xác định phạm vi: chậm toàn bộ hay một vài endpoint, bắt đầu từ lúc nào, có trùng với lần deploy nào không. (2) Xem metrics: CPU, RAM, độ trễ event loop, số kết nối DB, độ trễ p95/p99. (3) Xem APM hoặc tracing để biết thời gian tốn ở DB, API ngoài hay chính code. (4) Với DB: xem slow query log, chạy EXPLAIN, kiểm tra index, tìm N+1, xem có lock không. (5) Sửa nhanh bằng cache, index, hoặc rollback; về lâu dài thì tối ưu và thêm cảnh báo.

2. Muốn scale ngang API Node.js thì cần làm gì?

Làm cho app stateless: session để trong Redis, file upload lên S3, không cache quan trọng trong RAM, cron job chỉ chạy ở một nơi (hoặc dùng lock), WebSocket dùng Redis adapter. Sau đó đặt load balancer phía trước và cấu hình health check.

3. Read replica có vấn đề gì?

Replication lag: dữ liệu vừa ghi chưa kịp sang replica. Ví dụ user cập nhật hồ sơ rồi tải lại trang mà vẫn thấy dữ liệu cũ. Cách xử lý: đọc từ primary ngay sau khi ghi (read-your-writes), hoặc chỉ dùng replica cho báo cáo và những chỗ chấp nhận được dữ liệu hơi cũ.

4. Thiết kế chức năng đếm lượt xem bài viết cho trang có lượng truy cập lớn.

Không UPDATE DB ở mỗi lượt xem. Dùng INCR views:post:{id} trong Redis, rồi định kỳ (ví dụ mỗi phút) worker ghi dồn vào DB. Nếu cần đếm người xem duy nhất thì dùng HyperLogLog hoặc Set. Hiển thị số đọc từ Redis. Chấp nhận việc số liệu trong DB có thể trễ một chút.

5. Định lý CAP nói gì? Cho ví dụ chọn C và chọn A.

Khi xảy ra phân mảnh mạng (P), hệ thống phân tán chỉ đảm bảo được một trong hai: nhất quán (mọi node trả cùng dữ liệu mới nhất) hoặc sẵn sàng (luôn trả lời được). Chọn C cho thanh toán và tồn kho; chọn A cho lượt like, feed, số người đang online.

10. Microservices

Microservices là cách chia hệ thống thành nhiều service nhỏ, deploy độc lập, mỗi service phụ trách một miền nghiệp vụ và sở hữu dữ liệu riêng. Mức Middle không cần từng thiết kế cả hệ thống microservices, nhưng phải hiểu khi nào nên dùng, các service giao tiếp ra sao và xử lý lỗi phân tán thế nào.

10.3. Dữ liệu và transaction phân tán Bắt buộc

Database per service: service khác không được đọc thẳng DB của bạn mà phải gọi qua API hoặc nhận sự kiện. Vì không còn transaction dùng chung, các thao tác trải qua nhiều service phải dùng Saga.

Saga đặt hàng gồm một chuỗi transaction cục bộ; nếu một bước thất bại thì chạy các bước bù trừ (compensating action) theo chiều ngược lại:

  1. Order service tạo đơn ở trạng thái PENDING và phát sự kiện OrderCreated.
  2. Inventory service giữ hàng và phát StockReserved. Nếu hết hàng thì phát StockFailed, và Order chuyển đơn sang CANCELLED.
  3. Payment service trừ tiền và phát PaymentSucceeded. Nếu lỗi thì phát PaymentFailed; Inventory trả hàng lại kho (bù trừ) và Order hủy đơn.
  4. Order chuyển đơn sang CONFIRMED.
  • Choreography: các service tự lắng nghe sự kiện của nhau, không có điều phối viên. Đơn giản khi ít bước, nhưng khó theo dõi khi nhiều bước. Orchestration: có một orchestrator ra lệnh cho từng bước (tự viết, hoặc dùng Temporal). Dễ hiểu luồng hơn.
  • Transactional Outbox: vấn đề là ghi DB và gửi message không thể nằm trong cùng một transaction (ghi DB xong mà gửi message lỗi thì mất sự kiện). Cách làm: ghi sự kiện vào bảng outbox trong cùng transaction với dữ liệu, rồi một tiến trình riêng đọc outbox và gửi lên broker.
  • At-least-once delivery: broker có thể gửi trùng message, nên consumer phải idempotent (lưu messageId đã xử lý, hoặc dùng upsert).
ts
// Outbox: dữ liệu và sự kiện được ghi trong CÙNG một transaction
await prisma.$transaction(async (tx) => {
  const order = await tx.order.create({ data: { userId, items, status: 'PENDING' } });
  await tx.outbox.create({ data: { type: 'OrderCreated', payload: { orderId: order.id, items } } });
});
// Relay (worker riêng): đọc outbox chưa gửi → publish lên broker → đánh dấu đã gửi

// Consumer idempotent
async function onPaymentSucceeded(msg: { id: string; orderId: string }) {
  const done = await prisma.processedMessage.findUnique({ where: { id: msg.id } });
  if (done) return; // đã xử lý rồi → bỏ qua message trùng
  await prisma.$transaction([
    prisma.order.update({ where: { id: msg.orderId }, data: { status: 'CONFIRMED' } }),
    prisma.processedMessage.create({ data: { id: msg.id } }),
  ]);
}

10.4. Chịu lỗi và giám sát Nên biết

  • Timeout cho mọi lời gọi qua mạng. Không có timeout thì một service chậm sẽ kéo cả hệ thống chậm theo.
  • Retry với exponential backoff + jitter, và chỉ retry những thao tác idempotent.
  • Circuit breaker (thư viện opossum): khi service đích lỗi liên tục thì "ngắt mạch", trả lỗi hoặc dữ liệu dự phòng ngay thay vì tiếp tục gọi, sau một thời gian mới thử lại (trạng thái half-open).
  • Bulkhead: giới hạn tài nguyên (connection pool, số lời gọi đồng thời) cho từng phụ thuộc, để một phụ thuộc chậm không ăn hết tài nguyên của cả service.
  • Distributed tracing: mỗi request có một trace id được truyền qua mọi service (OpenTelemetry → Jaeger/Tempo). Log của mọi service đều kèm id này.
  • Triển khai: Docker + Kubernetes, mỗi service có pipeline CI/CD riêng. Ở mức nâng cao có service mesh (Istio, Linkerd) Điểm cộng.
ts
// Retry với exponential backoff + jitter
async function retry<T>(fn: () => Promise<T>, attempts = 4, base = 200): Promise<T> {
  for (let i = 0; ; i++) {
    try { return await fn(); }
    catch (e) {
      if (i >= attempts - 1) throw e;
      const delay = base * 2 ** i + Math.random() * base; // 200, 400, 800... + ngẫu nhiên
      await new Promise((r) => setTimeout(r, delay));
    }
  }
}
// Luôn đặt timeout cho lời gọi ra ngoài
const res = await retry(() => fetch(`${INVENTORY_URL}/reserve`, { method: 'POST', body, signal: AbortSignal.timeout(2000) }));

Câu hỏi ôn tập

Tự trả lời thành tiếng trước, rồi bấm vào câu hỏi để xem gợi ý.

1. Khi nào bạn chọn microservices? Khi nào không?

Nên chọn khi tổ chức có nhiều team cần deploy độc lập, miền nghiệp vụ có ranh giới rõ, các phần có nhu cầu scale hoặc công nghệ khác nhau, và đã có năng lực DevOps (CI/CD, giám sát, Kubernetes). Không nên với team nhỏ, sản phẩm mới chưa rõ miền nghiệp vụ, hoặc chưa có hạ tầng; khi đó nên dùng modular monolith và tách dần.

2. Distributed monolith là gì?

Là hệ thống được chia thành nhiều service nhưng vẫn dùng chung DB, phải deploy cùng nhau, và gọi nhau đồng bộ theo chuỗi dài. Nó có mọi độ phức tạp của microservices mà không có lợi ích nào: một service chết là cả chuỗi chết, sửa một chỗ phải deploy nhiều nơi.

3. Giao tiếp đồng bộ và bất đồng bộ giữa các service: khi nào dùng cái nào?

Dùng đồng bộ (REST/gRPC) khi cần kết quả ngay để trả lời user, ví dụ kiểm tra giá hay xác thực. Dùng bất đồng bộ (event qua broker) khi các bên không cần chờ nhau: gửi email sau khi đặt hàng, cập nhật thống kê, đồng bộ dữ liệu sang service khác. Bất đồng bộ giúp các service tách rời và chịu lỗi tốt hơn, đổi lại là phải chấp nhận eventual consistency.

4. Saga pattern là gì? Choreography khác orchestration thế nào?

Saga là chuỗi transaction cục bộ trải qua nhiều service; khi một bước lỗi thì chạy các bước bù trừ để hoàn tác những bước đã làm. Choreography: các service phản ứng với sự kiện của nhau, không có trung tâm. Orchestration: một orchestrator điều phối từng bước, dễ theo dõi và xử lý lỗi hơn khi luồng có nhiều bước.

5. Transactional Outbox giải quyết vấn đề gì?

Vấn đề "dual write": ghi DB thành công nhưng gửi message lên broker thất bại, hoặc ngược lại, khiến dữ liệu không nhất quán. Outbox ghi sự kiện vào một bảng trong cùng transaction với dữ liệu, rồi một relay đọc bảng đó và publish (có thể gửi trùng, nên consumer phải idempotent).

6. Vì sao consumer phải idempotent?

Vì hầu hết broker đảm bảo at-least-once: message có thể được gửi lại khi consumer chưa kịp ack, khi mạng lỗi hay khi có rebalance. Nếu không idempotent thì có thể trừ tiền hai lần hoặc gửi email hai lần. Cách làm: lưu id của message đã xử lý, dùng upsert, hoặc có ràng buộc unique trong DB.

7. Circuit breaker hoạt động thế nào?

Nó có 3 trạng thái. Closed: gọi bình thường và đếm số lỗi. Open: khi lỗi vượt ngưỡng thì ngừng gọi, trả lỗi hoặc dữ liệu dự phòng ngay. Half-open: sau một thời gian thì cho vài request thử; nếu thành công thì quay về closed, nếu không thì về open. Mục đích là không làm service đang lỗi thêm quá tải và không bắt người dùng chờ timeout.

8. Kafka khác RabbitMQ ở điểm nào?

RabbitMQ là message queue truyền thống: định tuyến linh hoạt, message bị xóa sau khi được ack, hợp cho task queue và command. Kafka là log phân tán: message được giữ theo thời gian cấu hình, nhiều consumer group đọc độc lập và đọc lại được, thông lượng rất cao, thứ tự được đảm bảo trong từng partition. Kafka hợp cho event streaming và analytics.

1. PHP-FPM xử lý request khác Node.js thế nào?

PHP-FPM có pool worker; mỗi request chiếm một worker từ đầu đến cuối, kể cả lúc chờ I/O, và trạng thái bị dọn sạch sau mỗi request (share-nothing). Node chạy một process với event loop, trong lúc chờ I/O thì xử lý request khác, và process sống lâu nên trạng thái global còn lại qua các request. PHP vì thế an toàn hơn về rò rỉ trạng thái; Node chịu được nhiều kết nối đồng thời hơn và hợp với realtime.

2. Trait trong PHP là gì? Khác interface thế nào?

Trait là cách dùng lại code (method, thuộc tính) giữa các class mà không qua kế thừa; dùng bằng use TraitName. Interface chỉ khai báo hợp đồng, không có cài đặt (từ PHP 8 vẫn vậy). Một class implement được nhiều interface và dùng được nhiều trait.

3. Giải thích SOLID kèm ví dụ cho chữ D.

S: mỗi class một trách nhiệm. O: mở rộng mà không sửa code cũ. L: class con thay được class cha. I: interface nhỏ, chuyên biệt. D: phụ thuộc vào abstraction. Ví dụ cho D: OrderService nhận PaymentGateway (interface) qua constructor thay vì tự new StripeClient(). Nhờ vậy đổi sang VNPay hay mock khi test chỉ cần bind một cài đặt khác trong container.

4. Service Container và Service Provider trong Laravel làm gì?

Container quản lý việc tạo object và tự inject phụ thuộc qua type hint (bind, singleton). Service Provider là nơi đăng ký binding (register) và khởi tạo (boot: route, event, macro). Bên NestJS tương đương là Module + Provider.

5. Làm sao phát hiện và sửa N+1 trong Laravel?

Phát hiện bằng Laravel Debugbar/Telescope (xem số query), hoặc Model::preventLazyLoading() để ném exception ở môi trường dev. Sửa bằng with(), load(), withCount(), hoặc JOIN khi cần lọc theo bảng quan hệ.

6. Mass assignment là gì và Laravel chống nó thế nào?

Là khi gán thẳng toàn bộ input vào model (User::create($request->all())), kẻ tấn công có thể gửi thêm is_admin=1. Laravel chặn bằng $fillable (danh sách cho phép) hoặc $guarded. Tốt nhất là chỉ dùng $request->validated().

Laravel: làm CRUD, trang quản trị, thương mại điện tử truyền thống rất nhanh vì hệ sinh thái có sẵn đủ thứ (auth, queue, mail). function promiseAll(items) {
  return new Promise((resolve, reject) => {
    const results = new Array(items.length);
    let done = 0;
    if (items.length === 0) return resolve(results);
    items.forEach((item, i) => {
      Promise.resolve(item).then((v) => {       // chấp nhận cả giá trị không phải promise
        results[i] = v;                          // giữ đúng thứ tự đầu vào
        if (++done === items.length) resolve(results);
      }, reject);                                // lỗi đầu tiên → reject ngay
    });
  });
}

  const results = new Array(items.length);
  let next = 0;
  async function worker() {
    while (next < items.length) {
      const i = next++;                 // an toàn vì JS đơn luồng

12.3. LRU cache

Đề bài: cache có dung lượng cố định; khi đầy thì loại phần tử lâu nhất chưa được dùng. Yêu cầu get/put chạy trong O(1).

js
class LRUCache {
  constructor(capacity) { this.capacity = capacity; this.map = new Map(); } // Map giữ thứ tự chèn
  get(key) {
    if (!this.map.has(key)) return -1;
    const v = this.map.get(key);
    this.map.delete(key); this.map.set(key, v);   // đưa lên cuối = vừa được dùng
    return v;
  }
  put(key, value) {
    this.map.delete(key);
    this.map.set(key, value);
    if (this.map.size > this.capacity) this.map.delete(this.map.keys().next().value); // xóa phần tử đầu = cũ nhất
  }
}

13.2. Quy trình làm việc hiệu quả Bắt buộc

  1. Khám phá: yêu cầu agent đọc và tóm tắt phần code liên quan trước khi sửa ("đọc module orders và giải thích luồng tạo đơn, chưa sửa gì").
  2. Lập kế hoạch: với việc lớn, bảo agent đề xuất kế hoạch (Claude Code có plan mode). Bạn duyệt, sửa kế hoạch rồi mới cho làm.
  3. Làm từng bước nhỏ: mỗi lần một thay đổi có thể kiểm chứng được. Đừng giao "làm cả tính năng thanh toán" trong một câu.
  4. Kiểm chứng tự động: cho agent chạy test, lint, type-check và tự sửa đến khi pass. Tốt nhất là viết (hoặc cho agent viết) test trước, kiểu TDD.
  5. Review diff như review code đồng nghiệp: đọc từng thay đổi, chạy thử, kiểm tra trường hợp biên và bảo mật.
  6. Commit nhỏ, thường xuyên: để dễ quay lại nếu agent đi sai hướng.

Một yêu cầu tốt gồm: mục tiêu, ngữ cảnh (file và module liên quan), ràng buộc (không đổi API công khai, theo đúng convention), tiêu chí hoàn thành (test nào phải pass) và cách kiểm chứng.

Câu hỏi ôn tập

Tự trả lời thành tiếng trước, rồi bấm vào câu hỏi để xem gợi ý.

1. Coding agent khác gì so với chatbot hay autocomplete?

Autocomplete chỉ gợi ý vài dòng. Chatbot trả lời, còn bạn tự chép code và tự chạy. Agent tự đọc codebase, sửa nhiều file, chạy lệnh (test, lint, git), đọc kết quả và lặp lại cho đến khi đạt mục tiêu. Nhờ vậy agent làm được việc lớn hơn, nhưng cũng cần kiểm soát quyền và review kỹ hơn.

2. Bạn viết gì trong CLAUDE.md hoặc AGENTS.md?

Các lệnh build, test, lint; cấu trúc thư mục; quy ước code (framework, cách validate, cách đặt tên); quy định bắt buộc (mọi endpoint phải có test); và những điều không được làm (sửa migration cũ, commit .env). File nên ngắn, cụ thể, và được cập nhật như tài liệu dự án.

3. Làm sao bạn đảm bảo code do AI viết là đúng?

Có tiêu chí hoàn thành kiểm chứng được (test cụ thể), bắt agent chạy test, lint, type-check; đọc toàn bộ diff, đặc biệt phần test (xem agent có sửa test cho khớp với code sai không); tự chạy thử các trường hợp biên; review bảo mật theo OWASP; và không merge code mà mình không giải thích được.

4. Vì sao nên yêu cầu agent lập kế hoạch trước khi sửa code?

Để phát hiện agent hiểu sai yêu cầu ngay từ đầu, trước khi nó sửa hàng chục file. Duyệt và sửa một kế hoạch rẻ hơn nhiều so với gỡ lại code đã viết. Kế hoạch cũng chia việc thành các bước nhỏ, dễ review.

5. Prompt injection là gì và ảnh hưởng thế nào tới coding agent?

Là khi nội dung agent đọc được (README, issue, comment, trang web, output của tool) chứa câu lệnh giả dạng hướng dẫn, khiến agent làm việc ngoài ý muốn, ví dụ gửi secret ra ngoài hay chạy lệnh nguy hiểm. Phòng tránh: giới hạn quyền, bắt agent xin phép với lệnh nguy hiểm, không cấp credential production, chạy trong sandbox hoặc container, và xem lại các hành động agent định làm.

6. Bạn quản lý context của agent thế nào khi làm việc dài?

Mỗi việc độc lập dùng một phiên mới; khi phiên quá dài thì tóm gọn (compact) hoặc ghi tiến độ ra file rồi bắt đầu lại; chỉ đưa những file liên quan; giao việc tìm kiếm rộng cho subagent; viết sẵn quy ước vào CLAUDE.md để khỏi phải nhắc lại.

7. Khi nào bạn KHÔNG dùng agent?

Khi chính mình còn chưa hiểu bài toán; khi cần quyết định kiến trúc hay đánh đổi nghiệp vụ; khi thao tác trực tiếp trên dữ liệu production; khi kết quả không kiểm chứng được tự động; hoặc khi chính sách công ty không cho đưa code hay dữ liệu đó vào công cụ AI.

8. Hook khác gì so với ghi quy tắc vào CLAUDE.md?

CLAUDE.md là hướng dẫn: agent đọc và cố gắng làm theo, nhưng có thể quên hoặc bỏ qua. Hook là lệnh do công cụ tự động chạy theo sự kiện (sau khi sửa file, trước khi chạy lệnh), nên quy tắc luôn được áp dụng. Ví dụ: tự format sau mỗi lần sửa, chặn việc sửa file .env.

14.4. Mẹo làm bài Bắt buộc

  • Câu điền từ: đọc ngay hai từ đứng trước và sau chỗ trống để biết cần từ loại gì (danh, động, tính hay trạng từ), sau đó mới xét nghĩa. Nhiều câu làm được trong 10 giây mà không cần hiểu hết câu.
  • Tìm dấu hiệu thì: since/for là hiện tại hoàn thành; yesterday/ago/last là quá khứ đơn; next/tomorrow là tương lai; by the time + quá khứ là quá khứ hoàn thành.
  • Đọc hiểu: đọc câu hỏi trước, rồi tìm từ khóa trong bài (tên người, ngày giờ, con số). Đáp án đúng thường diễn đạt lại ý trong bài bằng từ khác; đáp án lặp nguyên văn từ trong bài lại hay là bẫy.
  • Câu có NOT hoặc EXCEPT thì loại dần các đáp án được nhắc trong bài.
  • Không để trống câu nào nếu sai không bị trừ điểm. Câu quá khó thì đánh dấu và quay lại sau.
  • Luyện tập: 30 phút mỗi ngày trong 3–4 tuần: 15 phút ngữ pháp và từ vựng, 15 phút đọc một email hoặc bài báo ngắn. Làm 2 đề TOEIC Reading có bấm giờ trước ngày test.

1. Viết email (100–120 từ) xin nghỉ phép 2 ngày và nói rõ ai sẽ hỗ trợ công việc của bạn.

Kiểm tra: có mục đích ngay câu đầu, có ngày cụ thể, có người thay, có lời cảm ơn.

2. Viết email trả lời khách hàng báo lỗi "không đăng nhập được".

Gợi ý: cảm ơn và xác nhận đã nhận thông tin ("Thank you for reporting this issue."); nói bạn đang làm gì ("Our team is investigating it now."); xin thêm thông tin ("Could you tell us which browser you are using and send a screenshot of the error?"); cam kết thời gian ("We will update you within two hours."); ký tên. Tránh đổ lỗi và tránh hứa chắc chắn sửa xong khi chưa rõ nguyên nhân.

3. Phân biệt "by Friday" và "until Friday", cho ví dụ.

"By Friday" là hạn chót, việc phải xong trước hoặc đúng thứ Sáu: "Please send the report by Friday." "Until Friday" là kéo dài liên tục đến thứ Sáu: "The server will be under maintenance until Friday."

4. Phân biệt "efficient" và "effective".

Efficient là hiệu quả theo nghĩa ít tốn tài nguyên, thời gian ("an efficient algorithm"). Effective là đạt được kết quả mong muốn ("an effective solution to the problem"). Một giải pháp có thể effective mà không efficient.

16.1. Đặc tả dự án portfolio: "ShopLite"

Một trang thương mại điện tử nhỏ, đủ để thể hiện gần như mọi kỹ năng ở mức Middle. Khi nhà tuyển dụng hỏi "kể về dự án của bạn", đây sẽ là câu chuyện chính.

  • Backend (NestJS hoặc Express + TypeScript, PostgreSQL + Prisma, Redis): xác thực bằng JWT + refresh token rotation; phân quyền admin/khách; CRUD sản phẩm có phân trang cursor và tìm kiếm; đặt hàng có transaction chống bán vượt tồn kho; header Idempotency-Key khi tạo đơn; cache sản phẩm; rate limit đăng nhập; upload ảnh bằng presigned URL lên S3 (hoặc MinIO).
  • Bất đồng bộ: sau khi đặt hàng thì đẩy job gửi email xác nhận (BullMQ); thông báo trạng thái đơn hàng realtime qua SSE hoặc WebSocket.
  • GraphQL: endpoint /graphql cho dashboard admin (doanh thu, top sản phẩm), có DataLoader và giới hạn độ sâu query.
  • Frontend (React + Vite hoặc Next.js, TanStack Query, Zustand, Tailwind): danh sách, chi tiết, giỏ hàng, thanh toán giả lập, trang admin; có optimistic update và lazy load route.
  • Chất lượng: unit test, test API, một test E2E cho luồng mua hàng; CI chạy lint, type-check và test; Docker compose chạy toàn bộ bằng một lệnh.
  • README: sơ đồ kiến trúc, quyết định kỹ thuật và lý do chọn (ví dụ "Vì sao chọn cursor pagination"), hướng dẫn chạy, link demo.
